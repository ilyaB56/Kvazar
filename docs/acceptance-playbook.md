# Плейбук приёмки этапов (для суб-агента проверок)

Этот файл — инструкция для суб-агента, который выполняет механическую
часть приёмки работы чата разработки. Главный агент (архитектурный чат)
даёт суб-агенту ссылку на этот плейбук + конкретное задание на этап.
Вердикт «принято/не принято» выносит ТОЛЬКО главный агент; суб-агент
собирает факты и ничего не чинит.

## Окружение (дев-контур, машина основателя)

- Репозиторий: `C:\Users\днс\ZCodeProject\erp` (git, локальный).
- Контейнеры: `erp-api-1`, `erp-worker-1`, `erp-beat-1`, `erp-web-1`
  (:8080), `erp-db-1` (postgres, user `erp`, база `erp`),
  `erp-redis-1`. API: http://127.0.0.1:8000/api/v1 (прокси через web
  :8080/api/).
- Дев-админ: `admin@example.com` / `admin12345` (логин
  `POST /auth/login` → `access_token`).
- pytest/ruff НЕТ в живом контейнере — ставить при прогоне:
  `docker exec erp-api-1 sh -lc "pip install -q 'pytest>=8'
  'pytest-asyncio>=0.23' 'ruff>=0.4' && cd /app && python -m pytest -q
  tests 2>&1 | tail -2 && ruff check src tests 2>&1 | tail -1"`.
- Живые API-проверки — python-скриптом через stdin:
  `docker exec -i erp-api-1 python - <<'EOF' ... EOF` (stdlib urllib,
  requests НЕТ). База: `docker exec erp-db-1 psql -U erp -d erp -t -A -c "..."`.
- Bash — Git Bash на Windows: для docker compose с путями использовать
  `MSYS_NO_PATHCONV=1`; локальные пути кириллицей (`\днс\`) ломают
  некоторые инструменты — не строить на них URL.

## Порядок (механическая часть)

1. **Репозиторий**: `git log --oneline -5`, `git status --short`;
   сверить хэши/темы коммитов с заданием; дерево должно быть чистым.
2. **Прогоны**: pytest + ruff (команда выше); зафиксировать цифры
   (сколько passed, был ли рост против прошлого этапа — говорит
   главный агент).
3. **Живые API-проверки по типу этапа** (главный агент перечисляет
   конкретные пункты). Универсальные паттерны:
   - каждый прогон создаёт свои сущности с уникальным тегом
     `tag=uuid4().hex[:6]` (имена/sku/email вида `qa-...-{tag}`) —
     приёмка идемпотентна и не трогает чужие данные;
   - суммы/количества сравнивать как `Decimal` (в API строки вида
     «150.0000» / «2000.00» — форматы разнятся, это допустимо);
   - ошибки ожидать кодами в теле: `insufficient_stock`,
     `over_receipt`, `over_shipment`, `kind_mismatch`,
     `serial_not_found`, `has_subsequent_moves`;
   - readonly-роль: GET → 200, мутации → 403;
   - события: `GET /events/outbox?event_name=...&limit=5`.
4. **Отчёт** — строго формат:

```
РЕПОЗИТОРИЙ: <hash> <theme> …; дерево чистое/грязное (что осталось)
ПРОГОНЫ: pytest N passed; ruff чист/ошибки
API-ПРОВЕРКИ: OK n / FAIL m
  OK  <название проверки> [фактическое значение]
  FAIL <название> <ожидалось> <получено> <тело ответа до 120 симв.>
НЕОЖИДАННОЕ: <поведение, не совпадающее со спекой/планом, или «нет»>
ТЕСТ-ДАННЫЕ: создано <перечень qa-*>, можно чистить/оставить
```

## Правила

- Ничего не исправлять, не коммитить, не перезапускать стек без нужды
  (если стек лежит — сообщить, не поднимать самому).
- Не трогать данные вне своих `qa-*` сущностей.
- Браузерные проверки НЕ выполнять (вне компетенции суб-агента).
- При странном поведении не гадать — зафиксировать факт в «НЕОЖИДАННОЕ»
  с телом ответа.
