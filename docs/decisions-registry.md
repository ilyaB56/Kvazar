# Реестр решений проекта (архитектурный чат)

Единая точка правды о всех принятых решениях и их статусе. Дополняется
после каждого сеанса архитектурного чата. Если решения нет здесь и в ADR —
его официально не существует.

Условные статусы: **принято** (обязательно к исполнению), **предложено**
(ждёт обсуждения/ADR), **реализовано**, **долг** (осознанный, с триггером).

## Продукт и клиенты

- **Название продукта: «Квазар»** (решение основателя 2026-09-03).
  Пишем кириллицей; «ТехноПром» в макете UI — только демо-организация,
  не бренд. Брендинг переезжает в этапах A/B редизайна (title, favicon,
  K-монограмма, i18n `brand.name`; проверку title в tests/smoke.py
  менять тем же коммитом). Нюанс: латиницей Quasar называется популярный
  Vue-фреймворк — для RU-сегмента не мешает, для выхода на EN-рынок
  написать кириллицей или переоценить. Проверка товарного знака — до
  первых продаж (рядом с задачей лицензий). *Статус: принято.*

- **Целевое позиционирование**: управленческий учёт + интеграционный хаб +
  ИИ для МСБ. Не конкурируем с 1С в бухгалтерии — кормим её данными
  (модуль sync_1c в перспективе). FI-модуль — позже, только со специалистом
  по бухучёту. *Статус: принято.*
- **Первые клиенты**: пилоты из своего круга → digital-студии/агентства →
  селлеры маркетплейсов (Ozon/WB). 3–5 бесплатных пилотов за кейсы и
  обратную связь. *Статус: принято.*
- **Приоритет коннектеров под пилотов**: банк (Т-Бизнес/Сбер API), Ozon/WB,
  Telegram-уведомления, выгрузка в 1С. *Статус: принято.*

## Распространение и лицензии

- Модель: **SaaS (хостим) + коробка (on-prem у клиента)**, одна кодовая
  база, профили развёртывания. *Статус: принято.*
- **Лицензии**: офлайн-ключ Ed25519 (клиент, модули, срок, число юзеров);
  проверка подписи локально, без «звонков домой»; активация → мастер
  создания админа (пользователь сам придумывает логин/пароль). *Статус:
  принято концептуально; ADR-кандидат; реализация — до первой продажи.*
- «Exe-приложение» = браузер + локальный сервер (docker под капотом);
  десктоп-оболочка (Tauri/Electron) — опционально позже, чисто психологически.

## Архитектура развёртывания

- Профили: **all-in-one** (всё у клиента, как сейчас), **local + облачный
  хаб** (данные у клиента, интеграции у нас за подписку; хаб на их сервере —
  доп. тариф), **SaaS**. *Статус: принято.*
- **Мост `hub_link`**: очередь доставки событий хаб↔локальная часть;
  инициатива подключения — от клиента (pull/push), идемпотентность.
  *Статус: принято концептуально; ADR-кандидат; до запуска облачного хаба.*
- **Мультитенантность SaaS** + изоляция компаний (row-level security).
  *Статус: долг, триггер — открытие SaaS внешним клиентам.*

## Принятые ADR (см. docs/adr/)

- **ADR-001**: сеть — только через интеграционный модуль (коннекторы).
  Реализовано + линтер. Долг-хвосты: allowlist доменов, журнал исходящих,
  сетевая изоляция контейнеров (P1/P2 security-plan).
- **ADR-005**: внутренняя структура модулей — слои router→service→models,
  направление зависимостей строго вниз, классы-ABC для точек расширения
  (эталон — BaseConnector), функции для бизнес-логики, деление на фичи
  при росте, циклические импорты запрещены. Принято 2026-08-22;
  референс-реализация — mgmt_accounting + connectors.
- **ADR-002**: `/api/v1`, контракты payload «добавлять можно, ломать нельзя».
  Реализовано.
- **ADR-003**: деньги/мультивалютность уровень 1 (валюта на операции,
  замороженный курс, rates, Decimal/NUMERIC, half-up до копеек).
  Реализовано. Долги: BASE_CURRENCY=константа RUB (триггер: несколько
  юрлиц), уровень 2 — переоценка/курсовые разницы.
- **ADR-007 (2026-09-03)**: закупки/склад/производство — фичи-подпакеты
  внутри `mgmt_accounting` (`features/{purchasing,inventory}`), общая
  схема БД, платеж+движение склада в одной транзакции. Выделение в
  отдельный модуль — только при собственном жизненном цикле домена.
  Уточнение основателю: модули и так живут в ОДНОЙ базе PostgreSQL
  (схемы, не отдельные БД) — требование «единая база» соблюдено по
  построению. *Статус: принято.*

## Фронтенд: дизайн и роли (решения 2026-09-03)

- **Источник дизайна**: макет основателя (демо-бренд «ТехноПром»;
  Next.js+Tailwind+shadcn прототип, 14 экранов) принят как
  дизайн-источник истины. Причина: текущий Element Plus-каркас «отдаёт ИИ»
  и отталкивает пользователей. *Статус: принято.*
- **Стек НЕ меняем (подтверждено основателем 2026-09-03: «я не говорю
  копировать техническую реализацию макета… он сам подойти должен» —
  бераем визуальный дизайн, реализация наша)**: Vue 3 + Vite остаётся;
  дизайн переносится — токены
  (oklch-палитра, радиус 0.625rem, тёмный сайдбар/светлый контент,
  light/dark) и структура экранов 1:1 из макета, Element Plus заменяется
  на собственные компоненты в стиле макета (Tailwind + подход shadcn-vue).
  Переиспользуем: auth/refresh-guard, api-client, i18n, денежные утилиты,
  ADR-001 (без CDN — иконки/шрифты в бандл). *Статус: принято.*
- **Гранулярные роли**: роль → набор разрешений «модуль × уровень»
  (уровни упрощены по макету: **rw / ro / none**, как в его матрице
  «Доступы и роли»), хранение в erp_core (roles + role_permissions),
  эндпоинт GET /api/v1/me/permissions, навигация UI строится из
  разрешений (пользователь видит только назначенное). Серверная проверка
  остаётся обязательной — скрытие в UI не защита. admin/user/readonly
  сохраняются как встроенные пресеты (матрица=user, миграция без смены
  поведения). Пункт поднят из security-plan P2 в активную задачу этапа
  UI. *Статус: принято; спека `docs/design/frontend-redesign-spec.md`
  (готова 2026-09-03, этапы A–H; эталон дизайна —
  docs/design/mockup/).*
- Командная палитра (Ctrl+K), канбан с drag-n-drop из макета — в бэклог
  UI-этапа (H). Центр уведомлений по просьбе основателя (2026-09-03)
  вошёл в этап A в v1-lite: панель по макету, наполнение только
  реальными событиями (упавшие синхронизации, бэкапы, предложения ИИ),
  прочитанность в localStorage; серверная версия — H.

## Ядро ресурсов (решения 2026-09-04)

- **Диагноз принят**: в системе нет управления ресурсами — главного,
  ради чего покупают ERP. Разбор модулей известных ERP (1С УНФ/ERP,
  МойСклад, Odoo, ERPNext, SAP B1, D365 BC): общее ядро всех —
  номенклатура, деньги, склад, закупки, продажи-документы; остальное
  (производство, HR, ОС, проекты, розница) — опции.
- **Решения основателя**: (1) пилоты с физическими складами И продавцы
  цифровых продуктов; цифровой «склад» = локация в нашей БД с поштучным
  учётом уникальных кодов; (2) блоки пользователя: складской/цифровой
  учёт + закупки + управленческий учёт (последний уже есть);
  (3) сборка-производство и перепродажа нужны; (4) порядок: сначала
  бэкенд ресурсов, экраны потом (этап I редизайна).
- **Механики заимствованы**: двойная запись движений между локациями
  (Odoo), «документ → проводки» с частичными исполнениями (1С/МойСклад),
  средняя себестоимость (стандарт 1С/МойСклад). Архитектурный дом —
  ADR-007 (фичи-подпакеты mgmt_accounting, единая схема/транзакции).
- Спека: `docs/design/resources-core-spec.md` (этапы A–E:
  склад-ядро → закупки → продажи → сборка → полировка). Развилки

  средняя взвешенная; взаиморасчёты лёгкие; минус запрещён по
  умолчанию, настройка `allow_negative_stock` (erp_core settings).
  *Статус: этап A (НСИ + склад-ядро) реализован 2026-09-04, коммит

## Коробочная версия — видение основателя (черновик, 2026-09-16)

Обсуждение архитектуры коробки после вопроса основателя «зачем Docker,
он же для разработчиков». Решения:

1. **Tauri-оболочка для ВСЕХ пользователей** — не только для сервера:
   каждый сотрудник ставит лёгкий Tauri-клиент (~5 МБ), который
   открывает нативное окно (без адресной строки, с иконкой в панели
   задач, нативные уведомления, автозапуск). Внутри — тот же веб-
   интерфейс с сервера. Паттерн Slack/Discord/Notion. Первая настройка:
   «Укажите адрес сервера» → IP → иконка на рабочем столе.

2. **Пользователь НЕ ДОЛЖЕН ВИДЕТЬ Docker** — установщик сервера
   (один .exe) ставит всё за кадром: Docker Engine + контейнеры +
   база + настройка сети. Пользователь видит только «Установить
   Квазар» → «Готово» → иконка. Docker — внутренняя деталь, как
   движок внутри автомобиля.

3. **Сервер-ПК**: любой всегда-включённый компьютер (мини-ПК, NAS,
   офисный сервер, старый ПК). Рекомендация для клиента: мини-ПК
   Intel NUC / Raspberry Pi 5 (15–25 тыс. ₽, 10 Вт, 24/7).

4. **Обновления**: уже реализовано (ADR-004) — авто-бэкап → миграция
   → health-check → откат при сбое; одна кнопка «Обновить».

5. **Нативная сборка** (один .exe без Docker внутри) — долгосрочная
   цель (~2–3 мес. работы): Python → бинарник, PostgreSQL →
   встроенная библиотека, Redis → встроенная очередь. Делать при
   появлении 5+ коробочных клиентов со слабым железом (4 ГБ RAM).

*Статус: черновик-видение; реализация после пилотов на VPS.*

### hub_link мост — план (решение основателя 2026-09-19)

**Этапы реализации (в план после пилотов):**

*Инцидент 2026-10-03 (5-я итерация): лог клиента «localappdata\Docker=1,
Docker Desktop.exe нет, docker.exe нет, мастер среды закрывается за 10

wsl --status: 9009 → elevated (UAC) wsl --install --no-launch →
код 0 → явное «перезагрузите и запустите установку снова» (продолжение
с места остановки), код ≠0 → инструкция для ручного выполнения.
Второй фикс: проверка сборки Windows ≥19044 (Win10 21H2+ / Win11) на
wpSelectDir — на старых сборках Docker аналогично ставит пустоту.
Полная цепочка инцидентов коробки на живой машине (5 итераций):
--always-run-service (код 3) → {programfiles}-константа → PATH-слепота
→ WSL2-компоненты. Урок: «тихая» установка чужих пакетов с кодом 0 НЕ
гарантирует результата — обязательна верификация артефакта (exe/CLI)
после установки.*
*Диалог VT удалён из установщика 2026-10-03 (6-я итерация): «Не удалось

машине и не давал ставить — WMI VirtualizationFirmwareEnabled ложно
равен False на любой Hyper-V/WSL2-машине, т.е. ровно на целевой

→ чистый вред. Реальный гейт — старт движка; финальная ошибка ожидания

компонентов / VT в BIOS). Заодно укреплена проверка WSL: wsl --status

«перезагрузите») — теперь три сигнала: --status=0, --version=0, ключ
реестра HKLM\…\Lxss. Правило: предварительные барьеры в установщике —
только на 100% надёжных сигналах; ненадёжный барьер хуже отсутствия
барьера.*

VT-диалог (см. выше). Осталось: проверки RAM/диска/сборки Windows,
