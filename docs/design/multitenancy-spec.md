Статус: **ревью архитектурного чата пройдено 2026-09-13; развилки §12
закрыты (решения = рекомендации), открытые вопросы §13 закрыты (см.
конец файла); к утверждению основателем** · Дата: 2026-09-13 ·
Чат: архитектурный (триггер реестра «SaaS внешним клиентам» НАСТУПИЛ

## 1. Контекст и решения основателя

Реестр решений («Архитектура развёртывания») числил мультитенантность
долгом с триггером «открытие SaaS внешним клиентам». 2026-09-12
основатель активировал триггер и принял решения:

1. Пилот один, торопиться некуда — делать **нормальную**
   мультитенантность, а не минимальный компромисс.
2. Один сервер, одна установка Docker — **несколько организаций**.
3. **Основатель = супер-админ платформы**: заводит организацию и
   админа этой организации.
4. Админ организации добавляет своих сотрудников (создание учёток уже
   работает — `POST /users`, `src/core/router.py:419`).
5. **2FA (TOTP) — только для роли руководителя** (админ организации);
   сотрудники — без 2FA, восстановление через руководителя.
6. **Восстановление пароля — вариант «В»**: и сброс админом платформы,
   и email-ссылка (SMTP-коннектор уже есть — переиспользовать,
   `src/modules/integrations/connectors/smtp.py`).

Попутно закрывается дыра P1 из security-plan (п. 6 «2FA TOTP») и дыра
as-is «сменить чужой пароль в системе вообще некому» (§3).

Термины (глоссарий спеки):
- **Организация** — тенант: изолированный контур данных (учёт, склад,
  CRM, документы ИИ, коннекторы). Хранится в `erp_core.companies`
  (оживляем, см. Р5).
- **Платформа** — установка ERP целиком: сервер + Docker + БД, которыми
  управляет супер-админ платформы.
- **Супер-админ платформы** — пользователь с `is_platform_admin=true`,
  без организации; видит все организации, управляет ими и сбрасывает
  пароли.
- **Админ организации** — пользователь с ролью `admin` внутри своей
  организации (существующая роль, `src/core/models.py:39`).
- **Сотрудник** — пользователь организации с любой другой ролью.

## 2. Ключевые принципы

1. **Организация — обязательный контекст данных.** Любая строка
   бизнес-данных принадлежит ровно одной организации (`company_id NOT
   NULL`). Общие для всех — только платформенные справочники (виды
   документов, единицы, курсы ЦБ, каталог коннекторов, рецепты).
2. **Контекст живёт в JWT.** Клейм `org` (UUID организации или null для
   платформенного контекста) + `pl` (is_platform_admin). Все запросы
   модулей фильтруются по `org` из токена, а не по `users.company_id` —
   чтобы переключение супер-админа между организациями работало без
   правки пользователя. ApiPrincipal (X-API-Token) наследует организацию
   владельца токена.
3. **Один вход — один сеанс — много контекстов.** `auth_sessions`
   (sessions-security §2.1) не меняется: sid один; выбранная организация
   — атрибут пары токенов, переключение контекста перевыпускает пару,
   не создавая новый сеанс.
4. **Изоляция — два рубежа.** Primary: явный фильтр `company_id` в
   сервисном слое через единую зависимость ядра `CompanyScoped` +
   инвариантные тесты «чужая организация не видит» на каждом списковом
   эндпоинте. Second line: PostgreSQL RLS (этапность — развилка Р1).
5. **2FA защищает руководителя, восстановление — без него самого.**
   TOTP обязателен для админа организации; вход админа двухфазовый;
   резервные коды показываются один раз; сброс 2FA — только супер-админ
   платформы (аудит). Сброс пароля: платформа, админ организации (для
   сотрудников), email-ссылка (1 час, одноразовый токен).
6. **Никаких прямых импортов между модулями** (правило проекта).
   Письмо восстановления шлёт модуль integrations по событию ядра;
   ядро не ходит в сеть (ADR-001), токен в событие не попадает.
7. Деньги/количества — Decimal-строки (ADR-003), контракты — только
   расширяемы (ADR-002: в payload существующих событий добавляем
   `company_id` — это допустимое дополнение).

## 4. To-be: три уровня доступа

### 4.1 Супер-админ платформы (основатель)

- Единственный способ получить уровень — колонка
  `users.is_platform_admin=true` (заводится сидом/миграцией для
  существующего `admin@example.com`; выдача/снятие — только прямым
  редактированием БД, API для этого НЕТ — осознанно, чтобы уровень
  нельзя было эскалировать через UI).
- Не принадлежит организации (`company_id NULL`).
- Входит → видит **реестр организаций** (платформенный контекст) →
  выбирает организацию → получает пару токенов с `org` = выбранная.
  Переключение — в любой момент (§7).
- Платформенные полномочия: создание организации вместе с админом
  (временный пароль — показ один раз); редактирование/деактивация
  организации; просмотр журналов/событий/бэкапов (существующее
  admin-only из платформенного контекста); **сброс пароля любого
  пользователя**; **сброс 2FA** любого пользователя.
- Внутри выбранной организации супер-админ действует как её админ
  (роль `admin` у него сохраняется; level rw по `module_level`,
  `auth.py:170-172`).

### 4.2 Админ организации (руководитель)

- Пользователь с ролью `admin` и `company_id` своей организации.
- Всё, что умеет сегодня admin, но **в пределах своей организации**:
  учётки сотрудников, роли, настройки организации, коннекторы.
- **2FA TOTP обязательна**: первый успешный вход (пароль верный) без
  настроенной 2FA заводит мастер настройки — QR → код подтверждения →
  резервные коды. До завершения — полноценные токены не выдаются.
- Может сбрасывать пароли **сотрудников** своей организации (не свой).
  Собственный пароль — только через email-ссылку или супер-админа
  платформы (иначе сброс «для себя» обнулил бы смысл 2FA при захваченной
  сессии). У сотрудников 2FA нет, поэтому отдельного требования «код
  цели при сбросе» в v1 не возникает.
- НЕ может: видеть другие организации, сбрасывать 2FA (даже свою —
  только платформа), управлять платформенными настройками (бэкапы,
  обновления, каталог коннекторов).

### 4.3 Сотрудник

- Пользователь организации с любой ролью, кроме admin. 2FA не
  предлагается и не проверяется (решение основателя). Восстановление
  пароля — руководитель или email-ссылка.
- Все данные — только своей организации; матрица модулей rw/ro/none и
  делегирование (role-delegation-spec) работают внутри организации без
  изменений.

## 5. Модель данных

Миграции ядра — следующие номера единой цепочки (`erp/migrations/
versions/` сейчас до 0026_auth_sessions включительно): 0027+.

### 5.1 Организация (оживление `erp_core.companies`)

| колонка | тип | примечание |
|---|---|---|
| id (UUID) | PK | есть |
| name | String(255) | есть |
| inn | String(12) | есть |
| is_active | Boolean default true | новая: false = вход пользователей org запрещён |
| created_at | ts | есть |

При создании организации сидируются её стартовые данные (тем же
сервисом, что и миграционный seed): категории учёта, стадии воронки
CRM, склады (физический + цифровой + транзитные локации). Виды
документов (`doc_types`), единицы (`units`), курсы (`rates`) —
глобальные, не копируются; `doc_sequences` — ленивые, как сейчас.

Отношение к `contacts.company_id` («компания контакта»): deprecated,
новых записей не создаём; справочная роль компаний-контрагентов уже
покрыта `mgmt_accounting.counterparties` (+`contact_id`,
`models.py:67`). Удаление колонки — отдельная миграция v2 (развилка
Р5).

### 5.2 Пользователи и токены

`erp_core.users` — добавить:

| колонка | тип | примечание |
|---|---|---|
| company_id | UUID NULL FK companies | NULL только у платформенного админа; CHECK `(company_id IS NULL) = is_platform_admin` |
| is_platform_admin | Boolean default false | уровень платформы (не роль!) |

Миграция: создаётся организация «Основная» (name из настройки или
дефолт); все существующие пользователи, кроме `admin@example.com`,
получают её company_id; `admin@example.com` → `is_platform_admin=true`,
company_id NULL. Все существующие данные учёта/CRM/ИИ/коннекторы —
backfill company_id этой же организации (§5.3).

JWT: новые клеймы `org` (строка UUID или null) и `pl` (bool) в access и
refresh. `create_access_token`/`create_refresh_token` расширяются
необязательными параметрами (`src/core/auth.py:35-67`); без них —
токены без org (обратная совместимость во время этапа A). ВАЖНО:
`users.email` остаётся глобально UNIQUE — один человек = одна учётка =
одна организация (открытый вопрос О2).

### 5.3 Проброс company_id по модулям

Правило: **NOT NULL FK на корневые сущности и «журнальные» таблицы;
строки-дети — через родителя**. UNIQUE становится составным с
company_id.

`mgmt_accounting` (одна миграция модуля, обратимая — drop column +
вернуть простые UNIQUE):

| таблица | company_id | составные UNIQUE вместо глобальных |
|---|---|---|
| accounts | nullable → NOT NULL (backfill) | — |
| categories | + NOT NULL | — |
| counterparties | + NOT NULL | internal_code → (company_id, internal_code) |
| periods | + NOT NULL | (year, month) → (company_id, year, month) |
| doc_sequences | + NOT NULL | (doc_type_code, year) → (company_id, doc_type_code, year) |
| transactions | + NOT NULL | doc_number → (company_id, doc_number) |
| items | + NOT NULL | sku → (company_id, sku) |
| locations | + NOT NULL | name → (company_id, name); транзитные локации — на организацию (сидятся при создании) |
| stock_moves | + NOT NULL | — (журнал фильтруется напрямую) |
| item_serials | — нет | code_hash остаётся глобально уникальным (код — актив; глобальная уникальность только плюс); фильтрация через item |
| purchase_orders / sales_orders / receipts / shipments / production_orders / tech_cards | + NOT NULL | number → (company_id, number) |
| *_lines | — нет | через родителя |
| rates, doc_types, units | — глобальные | — |

`mini_crm`: `stages` + company_id NOT NULL, UNIQUE(company_id,
position); `deals` + company_id NOT NULL; communications/activities —
через deal.

`ai_agent`: `documents`/`chat_sessions`/`proposals` + company_id NOT
NULL; `chunks` — без колонки, RAG-поиск фильтруется join'ом по
documents (v1; денормализация — при миллионах чанков).

`integrations`: `connections` + company_id NOT NULL **или NULL =
платформенный коннектор** (см. ниже); `webhook_endpoints`,
`sync_jobs`, `field_mappings`, `notification_rules`,
`online_payments`, `item_mappings` + company_id NOT NULL;
`sync_runs`/`webhook_events`/`flow_runs` — через родителя; `recipes` —
глобальный каталог платформы (seed-рецепты), применение — через
connection организации.

**Платформенные коннекторы**: `connections.company_id IS NULL` — их
видит и настраивает только супер-админ платформы. В v1 один такой
коннектор — SMTP для системных писем (восстановление пароля; позже —
платформенные уведомления). Организации не видят чужие и платформенные
коннекторы; свои SMTP-коннекторы организации — для доставок кодов
покупателям (как сейчас, sales-automation §5.3).

Ядро: `settings` + company_id NULL (NULL = платформенная; чтение с
фолбэком «org → платформа», Р3); `events_log` + company_id NULL
(заполняется издателем; платформенные события — NULL);
`attachments` + company_id NOT NULL; `api_tokens` + company_id
наследуется от владельца (в tokens-ответе поле не светится).
`record_versions`, `event_outbox`, `revoked_tokens`, `auth_sessions`,
`backups`, `module_registry` — без изменений (журналы/инфраструктура
платформы).

### 5.4 2FA TOTP

`erp_core.user_totp`:

| колонка | тип | примечание |
|---|---|---|
| user_id | UUID PK FK users ON DELETE CASCADE | один секрет на пользователя |
| secret_enc | Text | Fernet по SECRETS_KEY (как credentials/цифровые коды) |
| confirmed_at | ts NULL | NULL = настроен, но не подтверждён |
| created_at / updated_at | ts | |

«2FA включена» = `confirmed_at IS NOT NULL`.

`erp_core.totp_backup_codes`: id, user_id FK, code_hash String(64)
(sha256, как api_tokens — `models.py:231`), used_at NULL, created_at.
10 кодов формата `XXXX-XXXX` (crypto-случайные, без неоднозначных
символов); показываются один раз; каждый расходуется единожды.

Новая зависимость бэкенда: `pyotp` (TOTP, окно ±1 шаг = ±30 с).
QR-код рендерит **фронтенд** локальной библиотекой из otpauth-URI
(без CDN — дух ADR-001); бэк отдаёт только URI и secret.

Обязательность: роль `admin` ИЛИ `is_platform_admin` (О1). Проверяет
её логин, а не require_module: пользователь без подтверждённой 2FA не
получает полноценные токены (§7.1).

### 5.5 Восстановление пароля

`erp_core.password_resets`:

| колонка | тип | примечание |
|---|---|---|
| id | UUID PK | |
| user_id | UUID FK users | индекс |
| token_hash | String(64) UNIQUE | sha256(urlsafe-32); токен в БД не хранится |
| expires_at | ts | created + 1 час |
| used_at | ts NULL | одноразовость |
| created_ip | String(64) | аудит |
| created_at | ts | |

Активный сброс = used_at IS NULL и не истёк. Новый запрос — новая
строка (старые не инвалидируются в пределах часа; не критично, ниже
rate limit).

## 6. Сценарии (Given/When/Then)

Основные:

- G: супер-админ платформы, верный пароль. W: `POST /auth/login`. T:
  200 `{mfa_required: true, mfa_token}` (2FA обязательна и О1 принята)
  → `POST /auth/mfa/verify` кодом → 200 `{platform: true,
  organizations: [список id/name]}`, токены **без org**; модульные
  эндпоинты — 403 `no_company_context`; `POST /auth/select-org` →
  новая пара с `org`; данные организации доступны.
- G: супер-админ в платформенном контексте. W: `POST /platform/orgs
  {name, inn, admin_email, admin_full_name}`. T: 201 — организация
  (сид категорий/стадий/складов) + пользователь роли admin с временным
  паролем в ответе **один раз** (`must_change_password=true`); аудит
  `platform.org.created`; событие в outbox с company_id.
- G: админ организации, 2FA ещё не настроена. W: вход с верным паролем.
  T: 200 `{mfa_setup_required: true, mfa_token}` → `POST
  /auth/totp/setup` (secret + otpauth-URI) → фронт рендерит QR →
  `POST /auth/totp/confirm {code}` (принят) → резервные коды показаны
  один раз → выдана полноценная пара токенов, создан сеанс
  (AuthSession).
- G: админ организации с включённой 2FA, повторный вход. W: верный
  пароль, затем верный 6-значный код. T: полноценная пара, ответ
  содержит `active_sessions` (модалка сеансов — без изменений).
- G: сотрудник без 2FA. W: вход с верным паролем. T: сразу полноценная
  пара — шаг 2FA не появляется.
- G: пользователь потерял пароль, у него есть email. W: `POST
  /auth/forgot-password {login}`. T: всегда 200 `{ok: true}` (не
  раскрывает существование); существующему активному пользователю —
  письмо со ссылкой `…/reset-password?token=…`; `POST
  /auth/reset-password {token, new_password}` по политике паролей →
  token_version+=1, все сеансы отозваны, строка used, аудит.
- G: админ организации, сотрудник забыл пароль. W: `POST
  /users/{id}/reset-password` (id из своей организации). T: временный
  пароль в ответе один раз, must_change_password, сеансы сотрудника
  убиты.

Альтернативные:

- G: супер-админ внутри организации А. W: `POST /auth/select-org
  {company_id: B}`. T: новая пара с org=B; прежняя пара остаётся
  валидной в другой вкладке (сеанс один, sid общий — §2.3); данные А
  из старой вкладки по-прежнему только А.
- G: админ организации, потерян телефон с аутентификатором. W: вход
  паролем + резервный код. T: вход разрешён, резервный код погашен
  (used_at); непотраченных кодов остаётся 9.
- G: резервные коды кончились/утрачены вместе с телефоном. W: супер-
  админ `POST /platform/users/{id}/totp/reset`. T: 200, user_totp и
  коды удалены, аудит `platform.totp.reset`; следующий вход админа —
  заново setup (обязательность сохраняется).
- G: письмо со ссылкой не дошло. W: повторный `forgot-password` через
  минуту. T: новая строка-токен, новое письмо; старая ссылка продолжает
  работать до своего часа (допустимо) — rate limit 3/час по login+IP.

Ошибочные (обязательные тесты):

- G: организация А создала товар со sku X. W: организация Б создаёт
  товар со sku X. T: 201 — допустимо (UNIQUE составной); список
  товаров А не содержит товар Б и наоборот.
- G: пользователь организации А, токен с org=A. W: `GET
  /accounting/items/{id_товара_Б}`. T: 404 (не 403 — не раскрываем
  существование).
- G: сотрудник организации А. W: `GET /users`. T: только пользователи
  своей организации; админ Б в списке отсутствует.
- G: админ организации. W: `GET /platform/orgs`. T: 403 (только
  платформенный контекст).
- G: вход админа, 2FA обязательна, настройка брошена на середине
  (mfa_token жив 5 минут). W: запрос данных по протухшему mfa_token.
  T: 401.
- G: `POST /auth/mfa/verify` с неверным кодом 6 раз подряд. T:
  429 (Redis-счётчик 5/60с по user_id, как у password-confirm,
  `src/core/router.py:245-253`); верный код после паузы — 200.
- G: `POST /auth/reset-password` с токеном, который уже использован.
  T: 410/404 `reset_token_invalid` (единый ответ за истёкшим/
  использованным/несуществующим).
- G: админ организации. W: `POST /users/{id}/reset-password` для
  пользователя другой организации. T: 404.
- G: `POST /auth/forgot-password` для email, которого нет. T: 200
  `{ok: true}` — то же, что для существующего.
- G: организация деактивирована (is_active=false). W: вход её
  пользователя с верным паролем. T: 403 `organization_disabled`;
  вебхуки её коннекторов продолжают приниматься и складываться в
  журнал (деньги провайдера не теряем), обработка flow — пауза до
  реактивации.

## 7. API

### 7.1 Изменения входа (`/api/v1/auth`)

- `POST /login` — тело `{login, password}` (login = email; после
  реализации role-delegation §12 — email или username, поле одно).
  Ответы (в порядке приоритета):
  1. неверный пароль → 401 (rate limit как сейчас);
  2. 2FA включена → `{mfa_required, mfa_token}` — короткоживущий JWT
     (type=mfa, exp 5 мин, без sid, без org);
  3. 2FA обязательна, но не настроена → `{mfa_setup_required,
     mfa_token}`;
  4. иначе — полноценная пара + sid + `active_sessions`; сотруднику и
     админу org подставляется их компания; супер-админу — токены без
     org + `organizations` (реестр).
- `POST /mfa/verify {mfa_token, code}` — код TOTP или резервный
  (резервный гасится). Успех → полноценная пара (для супер-админа —
  платформенный контекст + список организаций). AuthSession создаётся
  здесь (user_agent/ip — из этого запроса).
- `POST /totp/setup` (по mfa_token; для сотрудника — 403: не положено)
  → `{secret, otpauth_uri}`.
- `POST /totp/confirm {mfa_token, code}` → `{backup_codes: [...]}`
  (показ один раз) + если вход был по mfa_setup_required — сразу
  полноценная пара.
- `POST /auth/select-org {company_id}` (CurrentUser, только
  is_platform_admin, по refresh-токену тела, как logout-others) →
  новая пара с org=выбранная; sid сохраняется.
- `POST /auth/leave-org` → новая пара без org (платформенный
  контекст), sid сохраняется.

### 7.2 Тенант-контекст (зависимость ядра)

`CompanyScoped = Annotated[uuid.UUID, Depends(current_company)]` в
`src/core/auth.py`: возвращает org из JWT; если нет (платформенный
контекст без выбора) — 403 `no_company_context`; если организация
неактивна — 403 `organization_disabled`. Все списковые/точечные
запросы модулей обязаны фильтровать `Model.company_id == org`
(этап B переводит модули; ревью-чек-лист разработки дополняется
пунктом «новый эндпоинт — где фильтр company_id?»).

### 7.3 Платформенные эндпоинты (`/api/v1/platform`, требуют `pl`)

- `GET /orgs` — реестр (id, name, inn, is_active, users_count).
- `POST /orgs` — организация + админ + временный пароль (один раз).
- `PATCH /orgs/{id}` — name/inn/is_active.
- `POST /users/{id}/reset-password` — любой пользователь; временный
  пароль один раз; token_version+=1; ревок сеансов; аудит.
- `POST /users/{id}/totp/reset` — сброс 2FA (аудит).
- Платформенный SMTP: `GET/POST/PUT /platform/smtp` — тонкая обёртка
  над connections (code=smtp, company_id NULL); тест-связь как у
  обычных connections.

Существующее admin-only ядра (`/system/*`, `/roles`, `/events/*`,
`/admin/api-tokens`, `PUT /settings` для платформенных ключей)
доступно админу организации для своей org; платформенные операции
(бэкапы/обновления/платформенный SMTP) — только из платформенного
контекста (разграничение по scope-ключу настройки, Р3).

### 7.4 Сброс пароля организацией

- `POST /users/{id}/reset-password` (AdminUser организации, цель —
  сотрудник своей org, не себя) → временный пароль один раз,
  must_change_password, token_version+=1, аудит. Себе — 400 (свой
  пароль — смена со старым / email-ссылка / платформа).

### 7.5 Восстановление по email

- `POST /auth/forgot-password {login}` — публичный, rate limit 3/час
  по (login, ip); всегда 200; создаёт password_reset + событие
  `core.password.reset_requested` (payload: user_id, email, expires_at
  — **без токена**).
- `POST /auth/reset-password {token, new_password}` — публичный;
  политика паролей (`core/passwords.py`); успех: hash, token_version+=1,
  ревок всех сеансов, used_at, аудит `password.reset`.
- Обработчик события в модуле integrations (`events.on`) читает
  активный токен из `erp_core.password_resets` (контракт ядра — как
  users/contacts), строит ссылку `{web_url}/reset-password?token=…`
  (web_url — платформенная настройка), шлёт через платформенный
  SMTP-коннектор. Нет платформенного SMTP / ошибка — warn в журнал,
  повторная отправка повторным forgot-password; ретраи обработчика —
  стандартная механика диспетчера.

## 8. События (шина)

- Существующие события модулей: payload дополняется `company_id`
  (ADR-002 — расширение допустимо). Подписчики, которым нужна
  изоляция (notification_rules), фильтруются по нему.
- Новые: `platform.org.created` / `platform.org.updated` /
  `platform.org.deactivated`, `core.password.reset_requested` (без
  секретов), `core.totp.enabled` / `core.totp.reset` (кто, user_id;
  секретов нет).
- `notification_rules` — принадлежат организации: срабатывание только
  на события своей company_id (этап B).

## 9. Права (RBAC) и фронтенд

- `require_module` не меняется (уровень модуля — ортогонален
  организации); `module_level`/`effective_module_level` — без
  изменений. Изоляция — отдельной зависимостью `CompanyScoped` (§7.2).
- `/users` GET — срез своей организации (админ видит своих; после
  role-delegation rw-руководитель — тоже своих). Создание — как
  сейчас/по role-delegation, но компания наследуется от создателя
  (не из тела запроса).
- Фронтенд: экран «Выбор организации» после входа супер-админа (список
  + поиск; платформенный режим показывает реестр с действиями);
  переключатель организации в профиле; бейдж организации в шапке;
  мастер 2FA (QR → код → резервные коды с предупреждением «сохраните»);
  поле кода на втором шаге входа; страницы forgot/reset-password;
  i18n ru/en с первого дня (правило проекта).

## 10. Этапы и приёмка

Каждый этап — отдельный коммит; миграции обратимы (drop columns /
вернуть простые UNIQUE); деструктивных изменений нет; pytest + ruff +
smoke зелёные; приёмка суб-агентом по `docs/acceptance-playbook.md`.

- **A. Организации + пользователи + вход (ядро).** Миграция 0027:
  companies.is_active; users.company_id + is_platform_admin + CHECK;
  settings.company_id; events_log.company_id; события
  platform.org.*. JWT-клеймы org/pl; login/select-org/leave-org;
  CompanyScoped; `/platform/orgs` (+создание с админом и временным
  паролем); `/users` в срезе организации; деактивация организации.
  Приёмка: вход супер-админа → реестр → выбор org; /users изолирован
  (сценарии §6); CHECK не даёт сохранить пользователя без организации
  при is_platform_admin=false; обратная миграция прогоняется;
  существующий smoke зелёный без изменений данных (все — в «Основной»).
- **B. Проброс company_id в модули + изоляция сервисного слоя.**
  Миграции: mgmt_accounting (все таблицы §5.3 + составные UNIQUE),
  mini_crm, ai_agent, integrations (+платформенный SMTP-коннектор как
  NULL-company). Backfill «Основной». Фильтры во всех сервисах/
  роутерах модулей; company_id в payload событий; сиды при создании
  организации; notification_rules по org. Приёмка: параметризованный
  pytest «cross-tenant»: на каждом списковом эндпоинте — пустой список
  и 404 на прямой id; вторая организация создаёт совпадающие sku/номер
  без конфликтов; doc_sequences/periods независимы (закрытие периода в
  А не мешает Б); живой прогон двух организаций супер-админом;
  двойная запись/маржа/сторно — без регресса (существующие тесты
  проходят без правки ожиданий).
- **C. 2FA TOTP.** Миграции user_totp/totp_backup_codes; pyotp;
  двухфазный логин; setup/confirm; резервные коды; rate limit verify;
  сброс платформой; UI-мастер и второй шаг входа. Приёмка: сценарии
  §6 по 2FA живьём (QR проверяется валидатором TOTP по secret);
  неверный код ×6 → 429; резервный код гасится; сброс 2FA супер-
  админом → повторный setup; сотрудник входит без второго шага;
  ruff banned-api чист (криптография — только core/crypto).
- **D. Восстановление пароля + полировка.** Миграция
  password_resets; forgot/reset-password; сбросы (платформа/
  организация); событие + SMTP-обработчик + платформенный SMTP-
  эндпоинты; README («несколько организаций», «2FA», «восстановление»);
  OpenAPI-примеры; smoke-секция (создание второй организации +
  изоляция + письмо в mock-SMTP + сброс). Приёмка: полный цикл
  забытия пароля через email (mock-SMTP ловит письмо, токен работает,
  повтор токена — отказ); сброс админом организации; сброс платформой;
  одноразовость и час жизни проверены тестом на границе; audit-цепочка
  в events_log.

RLS (развилка Р1) — кандидат на этап E/v2 после приёмки A–D.

## 11. Что НЕ входит в v1

- Самостоятельная регистрация организаций (селф-сервис SaaS) —
  организации заводит только супер-админ платформы.
- Мультичленство: один email в нескольких организациях (О2).
- Тарифы/лимиты/биллинг организаций; лицензии на организацию.
- 2FA для сотрудников (email-код, SMS); 2FA-push/WebAuthn.
- RLS PostgreSQL как единственный рубеж (только second line, Р1).
- Отдельные БД/схемы на организацию (вариант «schema-per-tenant») —
  противоречит духу ADR-007 (общая схема, одна транзакция платежа и
  движения).
- Оргдрево/отделы между организациями; перенос пользователя между
  организациями (только деактивация + новая учётка).
- Выгрузка/удаление данных организации (152-ФЗ пакет — security-plan
  P2 п.14); белый лейбл (брендинг на организацию).
- «Вход по наблюдателю» (impersonation) супер-админом без выбора org.

## 12. Развилки (с рекомендациями)

- **Р1. Изоляция: RLS PostgreSQL vs фильтр в сервисном слое.**
  Реестр обещает row-level security, и «делать нормальную» — аргумент
  за RLS сразу. Но: одно соединение БД на всё (docker, общий
  суперюзер) — нужен `SET app.company_id` на сессию + политики на
  ~25 таблиц + обслуживание Celery/миграций/psql; цена высока, а
  ошибиться в политике так же легко, как забыть фильтр. Рекомендация:
  **сервисный фильтр (CompanyScoped) как primary на этапах A–B +
  обязательные инвариантные тесты cross-tenant на каждом списковом
  эндпоинте + пункт ревью-чек-листа**; **RLS — этапом E** как second
  line (политики `USING (company_id =
  current_setting('app.company_id')::uuid)`), после стабилизации
  схемы. Триггер ускорения: >5 реальных организаций или первый
  платящий внешний клиент.
- **Р2. Счётчики номеров: на организацию или общие.** Общий счётчик
  сохраняет глобальную уникальность номеров (ЗК-1 только один во всей
  установке) и упрощает поддержку, но смешивает нумерацию чужих
  бизнесов и выглядит ошибкой у клиента («почему у нас сразу ЗК-47»).
  Рекомендация: **на организацию** — `doc_sequences UNIQUE(company_id,
  doc_type_code, year)`, уникальность номеров составная; приватность
  нумерации важнее глобальной уникальности.
- **Р3. Настройки: глобальные vs на организацию.** Два хранилища
  (платформенные/организационные таблицы) чище типологически, но
  ломают существующий API `/settings` и экран Настроек. Только
  глобальные — нечестно для `allow_negative_stock` (у организаций
  разная дисциплина склада). Рекомендация: **колонка company_id NULL
  в settings + фолбэк «org → платформа» при чтении**; существующие
  строки становятся платформенными дефолтами; запись организационной
  строки — админом организации, платформенной — супер-админом.
  Технические ключи (бэкапы/обновления/web_url) — только платформенные
  (guard-список в ядре).
- **Р4. Коннекторы: на организацию или общие.** Общие коннекторы с
  «владельцем-организацией» в config — меньше строк подключений (один
  SMTP на всех), но: кредиты/токены организаций — это их секреты
  (Fernet один, но доступ к чужому connection = утечка), журналы
  смешиваются, аудит «кто настроил» размывается. Рекомендация:
  **коннекторы на организацию** (company_id NOT NULL), **кроме
  платформенных** (company_id NULL: SMTP системных писем) — их видит
  только супер-админ; каталог кодов коннекторов и рецепты — глобальные.
- **Р5. Сущность тенанта: оживить companies или новая таблица
  organizations.** Новая таблица семантически чище («компании» в
  ядре сегодня — справочник контрагентов контактов), но: остаётся
  третья похожая сущность (companies/organizations/counterparties) —
  гарантированная путаница терминов; `accounts.company_id` уже FK на
  companies (мигрировать); сама таблица companies практически пуста и
  «контактная» роль дублируется counterparties. Рекомендация:
  **оживить companies как «организация»**; `contacts.company_id`
  объявить deprecated (не заполнять, убрать из UI-подсказок);
  переименование таблицы — не делаем (миграция ради имени). Если
  арх-чат сочтёт двойную семантику опасной — альтернатива
  принимается, цена: +1 миграция accounts и пере-сид.

## 13. Открытые вопросы (с рекомендациями)

- **О1. Обязательна ли 2FA для супер-админа платформы?** Решение
  основателя называет только админа организации. Рекомендация:
  **да, обязательна** (максимальные полномочия = максимальный риск;
  механика та же, цена почти ноль). Если основатель против —
  оставить опциональной, но доступной.
- **О2. Один email в нескольких организациях** (бухгалтер на
  аутсорсе у двух клиентов). Рекомендация: v1 — запрещено
  (users.email UNIQUE сохраняется); при спросе — модель «членств»
  user_org_memberships как v2, сейчас её не закладывать.
- **О3. Очерёдность с role-delegation-spec** (утверждена, в очереди
  после мини-заезда; `/users` GET/создание и user_permissions
  проектируются в одной организации). Рекомендация: **этапы A–B
  мультитенантности — до реализации делегирования** (иначе /users и
  user_permissions придётся сразу переделывать под org-фильтр);
  делегирование тогда пишется поверх: выдачи внутри организации,
  анти-эскалация не меняется. Если делегирование уже в работе —
  ограничиться этапом A до него.
- **О4. Поведение вебхуков/синков деактивированной организации** —
  пауза с накоплением (§6, деньги провайдера не теряем) или полный
  отказ (410)? Рекомендация: пауза; автоматической чистки нет.
- **О5. «Прозрачность соседей»**: показывать ли админу организации
  факт, что установка общая (число соседей)? Рекомендация: нет —
  организация не должна видеть даже количество соседей; супер-админ
  видит всё.
- **О6. ИИ-модель на организацию**: у организаций общая локальная
  Ollama-модель (общий ресурс платформы) — подтвердить, что лимиты
  нагрузки (OLLAMA_NUM_PARALLEL=1) делятся между организациями
  честно; v1 — без приоритетов, общий пул. Рекомендация: принять как
  есть, зафиксировать в README.

## 14. Связь с другими спеками

- sessions-security-spec: не ломается — sid/сеансы не меняются,
  mfa_token сеансом не является; модалка сеансов работает после
  полного входа (после verify).
- role-delegation-spec: координация — О3; после этапа A выдачи и
  учётки неявно ограничиваются своей организацией (в спеку
  делегирования добавляется примечание, не переделка).
- sales-automation-spec: connections получают компанию; flow/
  online_payments — через connection; доставку кодов SMTP организации
  не трогаем; платформенный SMTP — только системные письма.
- updates-and-backups: бэкапы всей БД — платформенная операция (все
  организации сразу); проверка восстановления охватывает всю
  установку.
- security-plan: закрывает P1 п.6 (2FA) и дыру «некому сбросить
  пароль»; RLS-хвост остаётся (Р1).
