>    → видимый мастер Docker → ожидание движка (2×10 мин с
>    инструкцией про перезагрузку/ручной запуск). Тихая установка
>    удалена полностью (6 инцидентов: права, WSL2, PATH, циклы).
> 2. **Один реестр — ghcr.io, пакеты публичные**: образы api/web +
>    зеркала kvazar-db (pgvector:pg16) и kvazar-redis (redis:7-alpine)
>    из CI-джобы mirror-base. Никаких зависимостей от Docker Hub
>    (троттлится на клиентских сетях — инцидент «pull код 1»).
> 3. **Порядок фаз** (§3.7): вся фаза стека — на CurStepChanged
>    (**ssPostInstall**, НЕ ssInstall — файлы [Files] копируются между
>    ними): EnsureRuntime → GenerateEnv → compose pull → up -d →
>    health. `.env` генерируется ДО pull (POSTGRES_PASSWORD обязательна
>    при интерполяции) и **не перегенерируется, если существует**.
> 4. **Ключи шифрования генерирует контейнер образа** (docker run,
>    OS-PRNG в Linux), PowerShell машины — только фолбэк.
> 5. **Bootstrap-запрос отправляет контейнер изнутри сети стека**
>    (docker run --network kvazar_default, env в UTF-8, http.client на
>    web:80, HTTP-код = код завершения). Файлы из установщика — ANSI,
>    кириллица через них = битый UTF-8 (код 400).
> 6. **Health = /health** (корень приложения, nginx: точный
>    location = /health). /api/v1/health не существует.
> 7. **docker.exe вызывается по полному пути** ({commonpf} /
>    {localappdata} …\Docker\resources\bin) — PATH живого процесса не
>    видит только что установленный Docker.
> 8. **WMI не используется для VT** (ложно False под Hyper-V/WSL2 =
>    вся ЦА); RAM читается через StrToFloat (uint64 из WMI приходит
>    строкой, арифметика Overflow на >2 ГБ).
> 9. **Видимость всех длинных шагов**: скачивание Docker —
>    прогресс-страница с отменой; compose pull/up — консоль SW_SHOW.
>    Невидимое ожидание = «вечная загрузка» в глазах пользователя.
> 10. **Открытые пункты этапа B/C**: порт-детект/выбор при занятом
>     8080 (health-check читает «что угодно на порту» — ложные
>     срабатывания при соседнем стеке); автозапуск браузера после
>     успеха; индикация шагов после заполнения прогресс-бара.
>     Е2Е-прогон свежего .exe на чистом каталоге — обязательный пункт
>     релизного цикла (см. реестр: чек-лист коробки, 2026-10-04).

Решения PM (реестр, 2026-09-26): MVP = установил .exe → работает →
бэкапится → обновляется одной командой. Tauri-оболочка — v1.1;
hub_link — отложено (3+ удалённых коробок); нативная сборка — 5+ коробок;
темы SAP — не делать без запроса пилота.

## 1. Контекст и проблема

Сегодня развёртывание требует разработчика: git, docker compose up --build,
ручная правка .env, знание, что «профиль ai обязателен» (README §ИИ-агент).
Клиент МСБ этого не сможет. Видение основателя (реестр «Коробочная версия»,
2026-09-16): пользователь НЕ ДОЛЖЕН ВИДЕТЬ Docker — «Установить Квазар» →
«Готово» → иконка; Docker — внутренняя деталь, как движок в автомобиле.

Целевой сценарий v1: клиент скачивает один `quasar-setup.exe` (~50 МБ) →
мастер: «Установить» → невидимая установка среды выполнения → загрузка
образов → запуск → мастер первой настройки (организация + админ) →
открылся интерфейс на http://localhost:8080. Дальше: ежедневные бэкапы
(уже есть), обновление одной командой `quasar update` (ADR-004).

Границы версии: только Windows 10/11 x64; доступ сотрудников — браузер
по LAN (Tauri-клиент — v1.1); удалённый доступ — гайд по Tailscale
(документация, не код — решение 2026-09-19).

## 2. As-is (чем опираемся)

- **docker-compose.yml** — 6 сервисов: db (pgvector:pg16), redis, api,
  worker, beat, web (nginx, 8080), опциональный ollama (профиль ai).
  Все контейнеры `restart: unless-stopped` — комментарий в файле прямо
  говорит: «после рестарта Docker-движка контейнеры поднимаются сами
  (актуально для коробочной установки)». Автозапуск ОС сводится к
  «Docker Desktop стартует при входе → движок поднимает стек».
- **Секреты**: compose зашиты дев-значения (`JWT_SECRET:
  change-me-in-production`, `POSTGRES_PASSWORD: erp`); прод обязан
  задать `SEED_ADMIN_PASSWORD` (security-plan P0-5); в реестре долгов
  №5 — «CORS-origins и JWT_SECRET/SECRETS_KEY — прод-значения при
  выходе из дев-контура». Установщик обязан генерировать их сам.
- **Бэкапы**: реализованы (2026-08-23) — beat-расписание BACKUP_SCHEDULE,
  Fernet по BACKUP_KEY, retention, verify с test-restore, UI и
  `GET /api/v1/system/backups`; восстановление — командой
  `python -m src.backup restore --backup-id ... --drop` (README).
- **Обновления**: ADR-004 + реализовано (2026-08-23) — `deploy/update.py`:
  подпись Ed25519 манифеста → pre-flight → обязательный pre-бэкап →
  образы по дайджестам → up -d (миграции транзакционно) → health-check
  120 с → авто-откат. Ключ `update-public.pem` зашивается в дистрибутив.
- **Мастер настройки**: миграции и seed выполняются при старте api
  (`command: alembic upgrade head && python -m src.seed`); создание
  организации + админа — через `/api/v1/platform/orgs` (мультитенантность)
  или `/auth/signup` + одобрение. API для «первого входа» есть.
- **Наблюдаемость**: `docker compose ps` + `/health` у api; healthchecks
  уже объявлены в compose для db/redis.
- **Чего нет**: установщика как класса, registry-образов (сейчас
  `build: .` — сборка на хосте клиента!), CLI-утилит quasar-*, гайдов
  коробки.

## 3. To-be

### 3.1 Состав дистрибутива

| Артефакт | Что внутри |
|---|---|
| `quasar-setup.exe` (~50 МБ) | Inno Setup-установщик: файлы стека, генератор .env, CLI-утилиты, публичный ключ обновлений |
| `quasar-update.exe` / `quasar update` | обёртка над `deploy/update.py` (ADR-004) |
| `quasar-backup.exe` / `quasar backup` | ручной бэкап → `~/Quasar/backups/` |
| `quasar-restore.exe` / `quasar restore` | восстановление из файла бэкапа |
| Registry `ghcr.io/<org>/quasar-{api,web}` | образы; db/redis/ollama — публичные образы Docker Hub |

Каталог установки: `C:\Users\<user>\Quasar\` (не Program Files —
запись без UAC-элевации, Docker Desktop и так ставится per-user).
Подкаталоги: `stack/` (compose + .env), `bin/` (CLI), `backups/`,
`logs/`.

### 3.2 Технология установщика — рекомендация

**Inno Setup** (вариант Р1). Обоснование:

- нулевой рантайм (2–3 МБ оверхед), зрелый, скрипт в git = ревью;
- Pascal-скрипты покрывают всё MVP: проверку системы, скачивание,
  запуск сторонних установщиков с ожиданием, генерацию секретов,
  ярлыки, автозапуск (реестр Run), деинсталлятор «из коробки»;
- единый язык мастера (русский ISL-файл) + кодовая страница для
  «человеческих» сообщений.

Отвергнуты: NSIS (низкоуровневый, дольше писать то же самое);
Tauri installer (bundle — лишь обёртка WiX/NSIS, а Tauri как оболочка
вообще v1.1 — тащить рантайм Rust ради мастера рано); MSI/WiX
(корпоративная GEM-развёртка — не наш случай v1).

### 3.3 Поток установки (happy path)

```
quasar-setup.exe
 ├─ 1. Приветствие → лицензия → выбор папки (дефолт ~/Quasar)
 ├─ 2. Проверка системы (§3.4)
 ├─ 3. Среда выполнения (§3.5): Docker Desktop невидимо
 ├─ 4. Копирование стека + генерация .env (§3.6)
 ├─ 5. docker compose pull (registry, §3.7)
 ├─ 6. docker compose up -d + ожидание health (§3.8)
 ├─ 7. Мастер первой настройки (§3.9)
 └─ 8. Ярлык + автозапуск + «Готово, открыть Квазар»
```

Шаги 3–6 — один экран с прогресс-баром и стадиями на русском
(«Устанавливаем среду выполнения…», «Загружаем компоненты Квазара…»,
«Запускаем базу данных…», «Применяем настройки…»). Docker не
упоминается нигде в UI.

### 3.4 Проверка системы

| Проверка | Критерий | Действие при провале |
|---|---|---|
| ОС | Windows 10 1809+ / 11, x64 | блокирующее |
| RAM | ≥ 6 ГБ (с ИИ-профилем ≥ 8; рекомендация из README) | предупреждение: без профиля ai |
| Диск | ≥ 10 ГБ свободно на C: | блокирующее |
| Виртуализация | VT-x/AMD-V включена (без WSL2) | предупреждение: «включите виртуализацию в BIOS» — продолжить нельзя, пока выключена |
| WSL2 | установлен/не установлен | не блокирует: установщик Docker сам ставит WSL2 |
| Сеть | доступ к registry + dl.docker.com | блокирующее (в v1 офлайн-режима нет) |
| Порт 8080 | свободен | предупреждение + поле «другой порт» |
| Docker уже стоит | Engine отвечает | пропустить шаг 3 (используем существующий) |

Проверки — через WMI/реестр (Inno Pascal): `Win32_ComputerSystem`
(TotalPhysicalMemory), `GetLogicalDriveFreeSpace`,Hyper-V/
виртуализация — `systeminfo`-парс или WMI `Win32_Processor
VirtualizationFirmwareEnabled`.

### 3.5 Невидимая установка Docker Desktop

1. Скачать `Docker Desktop Installer.exe` (официальный стабильный URL)
   в `%TEMP%` — ~500 МБ, прогресс «Устанавливаем среду выполнения… %».
2. Запустить: `install --quiet --accept-license --always-run-service`
   (перелогин не требуем; добавление юзера в docker-users — установщик
   Docker делает сам для текущего пользователя).
3. Дождаться готовности Engine: poll `docker info` каждые 3 с,
   таймаут 10 мин. Docker Desktop после установки стартует сам;
   если нет — `"%ProgramFiles%\Docker\Docker\Docker Desktop.exe"`
   и снова poll.
4. Настройки VM под слабое железо (урок инцидента 2026-09-11):
   при RAM хоста ≤ 8 ГБ записать `%UserProfile%\.wslconfig`
   (memory=5GB, swap=2GB) ДО первого старта Engine; при 6 ГБ —
   memory=4GB и профиль ai не предлагать (§3.7).
5. Включить автозапуск Docker Desktop (settings.json
   `openUIOnStartupDisabled` + ярлык в автозагрузке / реестр Run).

### 3.6 Файлы стека и генерация .env

Копируем: `docker-compose.box.yml` (поставка из registry: `image:`
вместо `build:`, профиль ai вынесен в отдельный compose-override),
`deploy/keys/update-public.pem` (ADR-004).

Генерация прод-секретов (закрывает долг реестра №5):

| Переменная | Генерация |
|---|---|
| `JWT_SECRET` | `secrets.token_urlsafe(48)` — ≥ 32 байт (fix известного предупреждения) |
| `SECRETS_KEY` | Fernet-ключ (`Fernet.generate_key()`), серийные коды |
| `POSTGRES_PASSWORD` | `token_urlsafe(24)` (пишется и в `DATABASE_URL`) |
| `BACKUP_KEY` | отдельный Fernet-ключ (не равный SECRETS_KEY — README) |
| `SEED_ADMIN_PASSWORD` | НЕ задаётся — админ создаётся мастером §3.9 |
| `UPDATE_MANIFEST_URL` | https-URL нашего реестра манифестов |
| `CORS_ORIGINS` | `http://localhost:8080` + LAN-IP хоста |

Резервная копия .env — `~/Quasar/stack/.env` (напоминание в мастере:
«Файльчик .env — ключи от ваших данных, сохраните копию»). Также —
`quasar-*.exe` в `bin/` и в PATH-предложение при установке.

### 3.7 Registry-поставка (без bundling)

Образы НЕ вшиваем в .exe (решение PM; вывод гигиены диска 2026-09-12 —
«для коробки — поставка из registry, общие слои»). Установщик тянет:

- наши: `ghcr.io/<org>/quasar-api:<version>`, `quasar-web:<version>`
  (версия зашита в установщик; db/redis — с Diggest-пинами по
  манифесту релиза);
- публичные: `pgvector/pgvector:pg16`, `redis:7-alpine`;
- ollama — опция чекбоксом «ИИ-ассистент (нужно 8+ ГБ RAM)»:
  профиль ai + `AI_PROVIDER=ollama` + прогрев моделей
  (`pull_models`, README). По умолчанию чекбокс ВЫКЛ (стресс
  слабого железа; ИИ отложен до мощной коробки — решение 2026-09-11).

Требования к сети: доступ к `ghcr.io`/`registry-1.docker.io`/
`dl.docker.com`/нашему манифест-хостингу. HTTPS 443. Объём загрузки:
~2–3 ГБ (образы API+web+БД) + ~500 МБ Docker Desktop.

### 3.8 Запуск и health-check

1. `docker compose -f docker-compose.box.yml --project-name quasar up -d`.
2. Ожидание: db/redis healthchecks (compose), затем api `/health`
   (миграции + seed при первом старте), затем web `GET /` — общий
   таймаут 5 мин с понятным сообщением при провале + лог-файл
   `~/Quasar/logs/install.log` и кнопка «Показать журнал».
3. Автозапуск при включении Windows: Docker Desktop в автозагрузке +
   `restart: unless-stopped` у всех контейнеров (уже в compose) —
   отдельный Windows-сервис не нужен. Проверяется шагом 6 регресса.

### 3.9 Мастер первой настройки

Вариант Р (рекомендация): **мастер в установщике, создание через API**.
Экран: название организации, ФИО админа, email, пароль (с подтверждением,
подсказка политики: ≥8 символов, буква+цифра). Установщик после
health-check дергает:

1. `POST /api/v1/platform/bootstrap` — **новый эндпоинт** (one-shot,
   доступен только пока в системе 0 организаций): создаёт организацию
   + её админа + сиды (категории/склады/стадии CRM, ai-self-api
   connection — паттерн `POST /platform/orgs`), 2FA-дедлайн 7 дней —
   как у одобренных signup. После первого вызова эндпоинт отвечает 409.
   Альтернатива (отвергнута): сначала супер-админ из SEED, потом
   платформенные ручки — два экрана и лишняя сущность для клиента.

Открывается браузер на `http://localhost:8080` (или LAN-IP — показываем
оба адреса: «из сети: http://192.168.x.x:8080»). Ярлык на рабочем
столе → URL.

### 3.10 Деинсталляция

Inno деинсталлятор: остановить стек (`docker compose down`), спросить
«Удалить данные (база, бэкапы)?» — если да: `docker compose down -v` +
удалить `~/Quasar`. Docker Desktop не трогаем (не наше).

### 3.11 Обновление одной командой

`quasar update` (в bin/ + ярлык «Обновить Квазар» в меню Пуск):

1. `GET /api/v1/system/version` текущей установки vs манифест из
   `UPDATE_MANIFEST_URL` (ADR-004: подпись и min_supported проверяются
   ДО действий).
2. Дальше — существующий конвейер `deploy/update.py`: pre-flight →
   pre-бэкап → pull по дайджестам → `up -d` (миграции транзакционно)
   → health-check 120 с → **авто-откат при сбое** (бэкап + прежние
   образы). CLI-обёртка лишь транслирует вывод в консоль/лог
   `~/Quasar/logs/update.log`.
3. Поддержка N-2 (ADR-004); прыжки через unsupported — по цепочке.
4. Внутри Квазара уже есть уведомление-pull раз в 24 ч + баннер с
   changelog (README) — CLI добавляет «Обновить сейчас» → запуск
   `quasar update` (сообщение пользователю).

### 3.12 Бэкап/восстановление из коробки

- `quasar backup` — вызывает существующий бэкапер (celery-задача /
   `python -m src.backup` в контейнере api), копирует свежий
  `.quasarbak` из тома `erp_backups` в `~/Quasar/backups/` (человек
  видит файлы); выводит id и путь.
- `quasar restore --file <path>` — стоп api/worker/beat/web → файл в
  том → существующий restore (`--target erp --drop`) → `up -d` →
  health-check → откат на предыдущее состояние невозможен (данные
  перезаписаны) — поэтому restore требует явного `--yes` и печатает
  имя организации и дату бэкапа перед применением.

## 4. Сценарии (Given/When/Then)

### Основной
- G: чистая Windows 11, 8 ГБ RAM, интернет, прав админа ОС.
  W: пользователь запускает quasar-setup.exe и жмёт «Далее».
  T: все проверки пройдены; Docker Desktop установлен молча; образы
  скачаны; стек green за ≤ 20 мин; мастер создал организацию и админа;
  браузер открыл localhost:8080; вход админом работает; на рабочем
  столе ярлык «Квазар».
- G: установленная коробка, вышел релиз.
  W: `quasar update`.
  T: бэкап создан; образы заменены; health-check зелёный; версия в
  `/api/v1/system/version` новая; отчёт о шагах выведен.

### Альтернативные
- G: Docker Desktop уже установлен и Engine работает.
  W: установка.
  T: шаг 3 пропущен («среда уже готова»), свои контейнеры чужого
  Docker не тронуты; проект `quasar` изолирован (--project-name).
- G: установка с чекбоксом «ИИ-ассистент», RAM 16 ГБ.
  W: установка.
  T: поднят профиль ai, ollama-модель загружена (прогресс отдельно),
  `AI_PROVIDER=ollama` в .env.
- G: коробка установлена, ПК перезагрузили.
  W: вход в Windows.
  T: Docker Desktop стартует сам, движок поднимает стек
  (restart: unless-stopped), localhost:8080 отвечает без ручных
  действий (допустимо ожидание до 2–3 мин).
- G: сотрудник в той же LAN.
  W: открывает http://<IP-сервера>:8080.
  T: страница входа доступна (web слушает 0.0.0.0:8080).

### Ошибочные
- G: виртуализация выключена в BIOS.
  W: проверка системы.
  T: установка блокирована с инструкцией «включите VT-x в BIOS»;
  безальтернативно.
- G: Docker Engine не поднялся за 10 мин после тихой установки.
  W: установка.
  T: понятная ошибка + лог + ссылка на гайд; повторная попытка
  («Повторить») не переустанавливает Docker, а только ждёт Engine.
- G: порт 8080 занят.
  W: установка.
  T: предупреждение + поле выбора порта; ярлык и CORS ведут на
  выбранный порт.
- G: сеть оборвалась на шаге pull.
  W: установка.
  T: попытки возобновления; финально — ошибка с журналом; повторный
  запуск установки идемпотентен (продолжает с прерванного шага).
- G: health-check после обновления провалился.
  W: `quasar update`.
  T: авто-откат по ADR-004 (бэкап + прежние образы), стек на старой
  версии, событие system.rollback в аудите.
- G: два запуска quasar-setup.exe одновременно.
  W: установка.
  T: второй — мьютексом «Установка уже выполняется».
- G: восстановление бэкапа чужой организацией (не той, что в базе).
  W: `quasar restore --file x --yes`.
  T: restore проходит (это полная замена базы); перед применением
  пользователь видел название организации из бэкапа.

## 5. Модель данных / изменения в коде

Новых таблиц нет. Изменения:

1. `docker-compose.box.yml` (+ `docker-compose.ai.yml` override) —
   образы из registry, без `build:`, порты только у web (8080) и
   api на 127.0.0.1 (уже так). POSTGRES_PASSWORD/DATABASE_URL — из .env.
2. `POST /api/v1/platform/bootstrap` — one-shot создание организации
   (переиспользует сервисный слой `POST /platform/orgs`: сиды, 2FA
   -дедлайн, ai-self-api). 409 после первого успешного вызова.
3. `deploy/installer/` (новое): скрипт Inno Setup, Паскаль-хелперы
   (генерация секретов — через вызванный `openssl`/встроенный
   PowerShell RNG), прогресс-стейджинг, журнал.
4. `bin/quasar.cmd` — CLI-диспетчер (update/backup/restore/status),
   дёргает `docker compose run --rm api ...` / `deploy/update.py`.
5. CI: пайплайн релиза добавляет build+push образов в GHCR и сборку
   quasar-setup.exe (артефакт релиза); upgrade-path тест обязателен
   (ADR-004).

## 6. Влияние

- **Модули приложения**: без изменений (кроме bootstrap-эндпоинта в
  ядре платформы). ADR не меняются: ADR-004 исполняется, новых
  сквозных решений нет (установщик — внешний артефакт).
- **События шины**: system.updated/system.rollback — уже есть;
  добавляется `platform.org.bootstrap` (аналог platform.org.created).
- **API**: один новый эндпоинт; остальное — существующие.
- **RBAC**: bootstrap — без авторизации (доступен только при 0
  организаций, гасится 409 навсегда после).
- **Фронтенд**: не трогаем (v1 — браузер; Tauri — v1.1).
- **Документация**: README-коробки (Tailscale-гайд, .wslconfig,
  гигиена диска — перенести выводы реестра 2026-09-12).

## 7. Критерии приёмки (вход для QA)

1. Чистая Win11 VM (без Docker), 8 ГБ: quasar-setup.exe → «Готово»
   без единого упоминания Docker в UI; вход админом; п.4 §4 зелёный.
2. Все секреты в сгенерированном .env уникальны и ≥ требуемой длины
   (JWT ≥32 байт); дефолтовых `change-me` нет (grep по .env).
3. Docker уже установлен → установка не переустанавливает его.
4. Перезагрузка Windows → localhost:8080 отвечает ≤ 3 мин без ручных
   действий.
5.LAN-доступ с другой машины: вход сотрудником.
6. `quasar backup` → файл в ~/Quasar/backups/, verify (test-restore)
   проходит; `quasar restore --file` на чистой установке поднимает
   организацию из бэкапа.
7. `quasar update`: симуляция 0.x → 0.x+1 зелёная; симуляция
   сломанного релиза → авто-откат, стек жив на старой версии
   (паттерн приёмки 2026-08-23).
8. Bootstrap-эндпоинт: первый вызов создаёт орг+админа+сидами; второй
   — 409; при 1+ организациях — 409.
9. Проверки системы: VM с 4 ГБ RAM → предупреждение; порт 8080 занят
   → смена порта работает (ярлык ведёт верно).
10. ИИ-опция на 6 ГБ машине: чекбокс недоступен с пояснением.
11. Деинсталляция: без удаления данных — данные целы, повторная
    установка подхватывает; с удалением — ~/Quasar пуст.
12. Журналы install/update логов читаемы и прикладываются к тикетам.

## 9. Открытые вопросы (с рекомендациями)

- **Р1 Docker Desktop: embedded (~500 МБ в .exe) vs скачивание?**
  Рекомендация: скачивание при установке (лёгкий установщик ~50 МБ,
  свежая версия Docker). Embedded — только если пилоты пожалуются на
  медленный/нестабильный канал; тогда отдельный «offline»-билд.
- **Р2 Registry**: GHCR (бесплатный для приватных, интеграция с CI)
  vs Docker Hub (знакомее). Рекомендация: GHCR, публичные образы —
  код и так в коробке у клиента, приватность через обфускацию не
  защита.
- **Р3 Bootstrap vs seed-админ**: рекомендация — новый one-shot
  `/platform/bootstrap` (§3.9); альтернатива — SEED_ADMIN_PASSWORD
  в .env + первый вход. Вопрос архитектурному чату: принимаем ли
  «анонимный» эндпоинт (доступен лишь при пустой базе).
- **Р4 Windows Server / Hyper-V-хосты**: Docker Desktop требует
  клиентскую Windows; на Windows Server нужен Docker Engine напрямую
  или WSL. Рекомендация: v1 — только Win10/11, Server — по запросу.
- **Р5 Home/Pro и UAC**: тихая установка Docker требует прав админа
  ОС. Рекомендация: quasar-setup просит elevation один раз (manifest
  requireAdministrator), это допустимо для серверного ПК.
- **Р6 Обновление compose-файла**: `deploy/update.py` обновляет
  образы, но не docker-compose.box.yml. Рекомендация: включить
  compose-файл в манифест с дайджестом и обновлять его тем же
  конвейером (нужна маленькая правка update.py — в объём этапа B).

## 10. Решения ревью архитектурного чата (2026-09-26)

1. **Docker Desktop** → скачивание при установке (лёгкий установщик
   ~50 МБ, свежий Docker); embedded — только по жалобам на канал.
2. **Registry** → GHCR (бесплатный, CI-интеграция; публичные образы —
   код и так в коробке у клиента).
3. **Bootstrap endpoint** → ДА, принимаем `/platform/bootstrap` как
   one-shot без авторизации: доступен ТОЛЬКО при 0 организациях,
   после первого успешного вызова — 409 навсегда. Паттерн
   WordPress/Grafana first-run wizard. Окно уязвимости = только
   момент первой настройки до создания организации.
4. **Windows** → v1 только Win10/11 клиентская; Server — по запросу.
5. **Elevation** → один раз (requireAdministrator), стандартно для
   установщика серверного ПО.
6. **Compose-файл в манифесте обновлений** → ДА, включить в upgrade-
   manifest с дайджестом; маленькая правка deploy/update.py в этап B.
7. **.wslconfig** → установщик создаёт при RAM ≤ 8 ГБ (memory=5GB,
   swap=2GB — вывод инцидента 2026-09-11).
8. **ИИ-профиль** → опциональный чекбокс, недоступен при RAM < 8 ГБ.
