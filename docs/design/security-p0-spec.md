# Спецификация P0 безопасности (security-plan, пункты 1–5)

Задание для разработки. Основано на docs/security-plan.md (P0).
Порядок: RBAC → rate limit → отзыв сессий → HTTPS → парольная политика.

## 1. Enforce readonly-роли (security-plan P0.1)

Проблема: роль `readonly` объявлена, но mutating-эндпоинты доступны любому
аутентифицированному. Решение:

- В `core/auth.py` добавить экспортируемую зависимость
  `require_write = require_role("admin", "user")`.
- Применить ко ВСЕМ mutating-эндпоинтам (POST/PATCH/PUT/DELETE):
  - core: компании, контакты (`user`+); settings PUT и users — уже admin;
  - accounting: создание/правка/проведение/сторно/удаление черновика
    счетов, статей, контрагентов, транзакций (`user`+); delete-mark,
    close/reopen периода, rates POST — уже admin;
  - integrations: создание/запуск webhooks, mappings, sync-jobs —
    `admin` (конфигурация уровня системы; просмотр — любая роль).
- readonly — только GET, везде, без исключений.
- Тесты: `readonly` → POST транзакции = 403; `user` → 201.

## 2. Rate limit на логине (P0.3)

- Счётчик попыток в Redis: ключ `login_attempts:{ip}`, окно 60 с,
  порог 5 НЕудачных попыток; превышение → 429 + `Retry-After`.
- Реализация зависимостью на `POST /api/v1/auth/login`; успешный вход
  сбрасывает счётчик. Redis недоступен → fail-open (логин работает,
  ошибка в лог) — оффлайн-коробка важнее блокировки.
- Тест: 6 неудачных подряд → 429; после окна — снова 401/200.

## 3. Отзыв сессий и смена пароля (P0.4 + P0.5)

Миграция 0004 (обратимая): `erp_core.users.token_version INT NOT NULL
DEFAULT 0`; таблица `erp_core.revoked_tokens (jti UUID PK, user_id,
expires_at)`.

- В оба токена добавить claim `jti` (uuid) и `ver` (= token_version
  пользователя на момент выдачи). Проверка при каждом decode: `ver`
  совпадает с users.token_version, иначе 401 «Token revoked».
- `POST /api/v1/auth/logout` {refresh_token}: jti refresh-токена →
  в revoked_tokens (до его exp); аудит-событие `logout`. Access живёт
  свои 60 минут и умирает сам (задокументировать).
- `POST /api/v1/auth/change-password` {old_password, new_password}:
  проверка старого, политика нового (п. 4), bcrypt-хеш,
  `token_version += 1` (все сессии умирают — «выйти со всех устройств»),
  аудит `password.changed`. Требует повторного входа.
- Фронтенд: кнопка «Выйти» вызывает `/auth/logout` (best-effort, без
  блока UI при ошибке сети); маленький диалог «Сменить пароль» в меню
  пользователя (старый/новый/подтверждение); после смены — редирект на
  логин с тостом.

## 4. Парольная политика (P0.5)

- Минимум 8 символов — уже есть; добавить: минимум одна буква и одна
  цифра; запрет топ-500 частых паролей (файл-список в репо,
  сравнение в нижнем регистре).
- Единая функция проверки в core, используется при создании пользователя
  и смене пароля; ошибка 422 со списком правил.

## 5. HTTPS и публикация портов (P0.2)

- nginx (сервис `web`) умеет TLS: при `WEB_TLS=1` (env) слушает 443,
  сертификаты из volume `./deploy/certs` (self-signed инструкция в
  README: openssl одна команда), http→https redirect, заголовок HSTS.
  По умолчанию (dev) — как сейчас, 8080 без TLS.
- Порт API привязать к localhost: `127.0.0.1:8000:8000` в compose —
  наружу только через web-прокси. Dev-режим не ломается.
- Фронтенд-проверку не трогать (API относительный путь уже корректен).

## Приёмка (добавить в tests/smoke.py + ручные)

1. `readonly`-пользователь: GET /accounting/accounts — 200;
   POST /accounting/transactions — 403. `user`: POST — 201.
2. 6 неверных логинов подряд — 429 с Retry-After; через 60 с — снова 401.

8. Регресс: ruff, pytest (включая новые unit-тесты лимитера и
   token_version), smoke — всё зелёное; README дополнен (HTTPS-режим,

## Правила

- Вопросы по неоднозначностям — до кодинга. Секреты в логи не писать.
- Новые эндпоинты — с явной ролью (правило security-plan).
- Миграция обратимая; payload событий не менять (ADR-002);
  сетевых импортов вне коннекторов не появилось (ADR-001).
