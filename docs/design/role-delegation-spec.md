# Спека: делегируемая ролевая модель (наделение правами в пределах своих)

Статус: **ревью архитектурного чата пройдено 2026-09-11**; развилки §11
закрыты (Р1 user_permissions, Р2 немедленный каскад, Р3 создание
пользователей admin-only в v1, Р4 вкладка «Пользователи», Р5 вне v1);
чтение /users для rw-обладателей — ограниченным срезом
(id/email/name/is_active), создание и удаление — admin-only. УТВЕРЖДЕНА
основателем 2026-09-11; место в очереди — ПОСЛЕ мини-заезда. · Дата: 2026-09-11 ·
Чат: архитектурный (брифинг по отзыву основателя №2 п.1, 2026-09-10)

## 1. Контекст и проблема

Видение основателя: в организации иерархия — гендир (максимальные полномочия)
наделяет начальников направлений правами, почти максимальными в их сферах;
начальник направления наделяет начальников отделов в своей подобласти; те —
работников. Ответственность руководителя = право выдавать подчинённым роли
в пределах своей области и не выше своих полномочий. Цель: никому не нужно
вручную согласовывать каждую роль у админа.

Сегодня матрица «Доступы и роли» плоская: админ назначает каждому пользователю
одну роль-пресет. В организации от ~10 человек админ становится узким горлом,
хотя руководители сами знают, кому что открывать.

Граница v1 (требование арх-чата, не больше): **без оргдрева и отделов**.
Обладатель rw на модуль X выдаёт другим пользователям ro/rw только на X и
не выше собственных прав; отзывает только свои выдачи; каждая операция —
аудит + record_versions; admin — как сейчас; анти-эскалация обязательна
тестом. Профили МСБ/средний/крупный — описанием, без реализации (§10).

## 2. As-is (ссылки на код)

- Роли: `users.role` — текстовый ключ, FK на `roles.key`, у пользователя
  **одна** роль (`src/core/models.py:29-31`). `roles` — key/name/is_builtin/
  color (`models.py:38-49`); `role_permissions` — PK `(role_key, module)`,
  level `'rw'|'ro'`, отсутствие строки = `'none'` (`models.py:52-62`).
- Модули матрицы: `MODULES = ("accounting", "crm", "integrations", "ai",
  "system")` (`src/core/auth.py:149`).
- Проверка доступа: `module_level(db, role_key, module)` — по **роли**,
  admin всегда rw (`auth.py:152-165`); зависимость `require_module(module,
  level)` читает БД на каждом запросе, кэша нет (`auth.py:168-182`).
  Все модули уже переведены на неё (integrations, ai, mgmt_accounting,
  mini_crm — этапы D–G редизайна, реестр 2026-09-06/07).
- API прав: `GET /me/permissions` — эффективная матрица своей роли
  (`src/core/router.py:439-445`); `GET/POST /roles`,
  `PUT /roles/{key}/permissions`, `DELETE /roles/{key}` — admin-only
  (`router.py:448-539`).
- Пользователи: `GET/POST /users`, `PATCH /users/{id}` — admin-only
  (`router.py:218-270`); при смене роли никаких последствий по цепочке
  нет; деактивация поднимает `token_version` (`router.py:264-265`).
  «/users — admin-only признано правильным» (реестр, этап G).
- Аудит: `events_log` (`AuditEvent`: user_id, action, entity_type,
  entity_id, payload JSONB — `models.py:100-112`). Версии записей:
  `record_versions` (`RecordVersion`: entity_type, entity_id, changed_by,
  diff `{поле: {old, new}}` — `models.py:153-166`), хелпер
  `record_version(...)` (`src/core/versioning.py:17-36`).
- API-токены: `ApiPrincipal` ходит под собственной ролью токена,
  действия пишутся от владельца (`auth.py:66-80`, `models.py:197-216`).
- UI: матрица «Доступы и роли» по макету (`frontend/src/views/
  PermissionsView.vue`), навигация строится из `/me/permissions`
  (`frontend/src/stores/auth.ts:67`); спека редизайна §6.

Дыра as-is: единственный «выдаватель» прав — admin; персональных прав нет
совсем; смена роли пользователя не влияет на чужие доступы (их и не может
затронуть — прав больше некому выдавать).

## 3. To-be (целевое поведение, по ролям)

Принцип: **роли остаются пресетами** (админская зона, без изменений);
делегирование — персональная надстройка поверх ролей. Эффективный уровень
пользователя на модуль = `max(уровень роли, личная выдача)` по решётке
`none < ro < rw`. Надстройка может только **добавлять** доступ, не понижать
(понижение ниже роли — вне v1, §9/Р5).

**Админ** — всё как сейчас: создаёт пользователей, управляет ролями и
матрицей; плюс может выдать/отозвать любому персональное право на любой
модуль (его выдачи помечаются `granted_by = admin`).

**Руководитель (обладатель rw на модуль X)** — без обращения к админу:
- видит список пользователей (ограниченный набор полей) и **только свои
  rw-модули** как доступные к выдаче;
- выдаёт любому активному пользователю ro или rw **только на X**;
- отзывает **только выдачи, сделанные им самим** (`granted_by = он`);
- не может: выдать право на модуль, которого у него нет (анти-эскалация);
  выдать, имея только ro; выдать себе; отозвать чужую выдачу или выданное
  ролью.

**Работник (grantee)** — доступ по максимуму роль/личное появляется сразу,
без перелогина (права и так читаются из БД на каждый запрос). Личное ro
не даёт права выдавать (выдаёт только rw). Свои эффективные права видит в
`/me/permissions` (расширяется, ADR-002 — только добавлением полей).

**Каскад при потере собственных прав** (рекомендация Р2): когда у
пользователя исчезает rw на X (смена роли, отзыв его личной выдачи,
отзыв выше по цепочке) — все **его** выдачи на X откатываются рекурсивно
до фикспоинта, в одной транзакции, каждая с аудитом и record_versions.
Право, опирающееся на утраченное право, жить не может.

Каждая выдача/отзыв (включая каскадные): строка аудита `events_log`
(кто-кому-что: `{module, level, grantee}`) + версия в `record_versions`
пользователя-получателя.

## 4. Сценарии (Given/When/Then)

Основной:
- G: админ создал пользователя П, роль readonly; Р — руководитель с
  accounting:rw. W: Р выдаёт П `accounting: ro`. T: 200; у П эффективный
  accounting = ro (GET модуля 200, POST 403); в events_log —
  `permission.granted`; в record_versions П — diff
  `{"permission.accounting": {"old": "none", "new": "ro"}}`.
- G: Р выдал П accounting:ro. W: Р выдаёт П accounting:rw. T: 200, строка
  обновлена, `granted_by` = Р; у П rw.

Альтернативные:
- G: П получил accounting:ro лично. W: админ меняет роль П на user
  (accounting:rw по роли). T: эффективный = rw (max); личная строка
  остаётся, ни на что не влияет.
- G: Р выдал П accounting:ro. W: Р же отзывает. T: 200, строка удалена,
  эффективный уровень П = уровень его роли (none/ro); аудит
  `permission.revoked` + record_versions.
- G: админ выдал П crm:rw (Р не имеет crm). W: Р пытается отозвать эту
  выдачу. T: 403 (отзывать можно только свои выдачи; админ — любые).

Ошибочные (анти-эскалация — обязательные тесты):
- G: Р имеет только accounting:rw. W: Р выдаёт П `crm: ro`. T: **403**,
  строк не создано.
- G: Р имеет accounting:ro. W: Р выдаёт П `accounting: ro`. T: **403**
  (выдавать может только rw).
- G: Р — руководитель. W: Р выдаёт право самому себе. T: **422**.
- G: Р выдал П accounting:rw. W: П (теперь rw) выдаёт третьему
  `accounting: rw`. T: 200 — **это легально**: П обладает rw, цепочка
  делегирования разрешена (предел — собственные права, не «глубина»).
- G: Р выдал П accounting:ro; админ сменил роль Р на readonly. W:
  транзакция смены роли. T: выдача П откатывается каскадом (аудит
  `permission.revoked.cascade`), у П доступ по роли.
- G: неактивный пользователь. W: выдача ему права. T: 422; отзыв от
  неактивного невозможен (он не аутентифицируется — 401 на входе).

## 5. Модель данных

**Принято: пользовательская надстройка `user_permissions`.** Новая таблица
`erp_core.user_permissions` (миграция прямая и обратимая — drop table,
деструктивных изменений нет):

| колонка | тип | примечание |
|---|---|---|
| `user_id` | UUID FK `users.id` ON DELETE CASCADE | получатель |
| `module` | String(30) | ∈ MODULES; PK `(user_id, module)` |
| `level` | String(5) | 'rw' \| 'ro'; нет строки = none — симметрично role_permissions |
| `granted_by` | UUID FK `users.id` | кто выдал; определяет право отзыва |
| `granted_at` | DateTime(tz) | |

Индекс `granted_by` (кому искать выдачи при каскаде). Отсутствие строки =
none — та же конвенция, что у `role_permissions` (`models.py:52-62`).

Почему не `granted_by` в `role_permissions`: права там принадлежат **роли**,
а не пользователю — колонка не отвечает на вопрос «кому я выдал». Одна роль
назначается многим, у пользователя ровно одна роль (`models.py:29-31`) —
выдача «модуль X» нескольким людям разными руководителями в одну роль
не записывается.

Альтернатива «роли с владельцем» (руководитель создаёт личные роли-срезы
и назначает их) — отклонена для v1, разобрана в развилке Р1.

Enforcement: `module_level(db, role_key, module)` дополняется функцией
`effective_module_level(db, user, module)`: admin → rw; иначе
`max(level роли, level личной строки)`. `require_module` переходит на неё
(точка одна — `auth.py:168-182`; ApiPrincipal: у токена нет личных выдач,
ходит по роли токена — осознанная граница v1, задокументировать в docstring).

## 6. API и иерархия проверки

Новые эндпоинты (ядро, `/api/v1`):

- `GET /delegations` — «кого могу наделять»: `{grantable: {module: level}`
  (только rw-модули вызывающего), `grants: [{user_id, email, full_name,
  module, level, granted_at}]` — свои выдачи. Доступ: admin или обладатель
  rw хотя бы на один модуль.
- `GET /users/{user_id}/permissions` — `{role, role_permissions,
  personal: [{module, level, granted_by, granted_at}]}`. Не-admin видит
  все личные строки (чтобы видеть картину), но редактировать может только
  свои (см. ниже).
- `PUT /users/{user_id}/permissions` `{module, level}` — выдать/обновить
  (обновление перезаписывает строку, `granted_by` переходит к новому
  выдающему — last-writer-wins, фиксируется аудитом).
- `DELETE /users/{user_id}/permissions/{module}` — отозвать свою выдачу
  (admin — любую).

Иерархия проверки выдачи (порядок в коде, каждая — свой HTTP-код):
1. grantee существует, активен, ≠ выдающий — иначе 404/422.
2. module ∈ MODULES, level ∈ {ro, rw} — иначе 422.
3. Выдающий — admin → пропустить п.4. Иначе: эффективный уровень
   выдающего на module = **rw** — иначе 403 (анти-эскалация: и «нет
   модуля», и «есть только ro» — оба 403).
4. Запись: upsert строки + `AuditEvent(permission.granted)` +
   `record_version("user", grantee_id, diff, reason="delegation")` +
   при понижении своих прав grantee (нет в v1 — только добавление) —
   будущая точка каскада.

Отзыв: `granted_by = выдающий` или admin, иначе 403/404; удаление строки +
аудит `permission.revoked` + record_versions + **каскад**: транзитивно
отозвать выдачи, опирающиеся на утраченное право (фикспоинт-цикл по
`granted_by`, масштаб МСБ — десятки строк).

Затрагиваемое существующее:
- `PATCH /users/{id}` (смена роли) — после смены запуск каскада для
  этого пользователя как выдающего (`router.py:248-270`).
- `GET /users` — открывается обладателю rw ≥1 модуля (ограниченный набор
  полей UserOut; иначе руководителю некого выбирать) — Р3 затрагивает
  только создание, чтение открываем в v1.
- `GET /me/permissions` — добавить поле `granted: {module: level}`
  (личные), `permissions` остаётся эффективным максимумом (ADR-002:
  payload только расширяется).
- События шины: **не публикуем** (ядро, аудит в events_log достаточен);
  `core.permission.granted/revoked` в outbox — опция v2 для уведомлений.

## 7. Влияние

- **Ядро**: `auth.py` (effective level), `router.py` (4 эндпоинта +
  каскад в PATCH), миграция ~`0025_user_permissions` (после
  `0024_payments_flow`). Модули не трогаем — они уже на `require_module`.
- **RBAC**: `/roles` и создание пользователей — по-прежнему admin-only;
  `/users` (GET) — расширяется; матрица ролей не меняется.
- **Фронтенд**: вкладка «Пользователи» рядом с матрицей в «Настройки →
  Доступы и роли»: список пользователей, у каждого — роль (текст) и
  личные доступы чипами; **выдающий видит только свои rw-модули** как
  редактируемые (ro-модули и чужие — не показываются редактируемыми);
  admin видит все + пометку «личное/роль». i18n-ключи с первого дня.
- **Тесты**: анти-эскалация — обязательный блок (§8, этап B).

## 8. Этапы и приёмка

**A. Модель + enforcement (бэкенд).** Миграция `user_permissions`;
`effective_module_level`; `require_module` на ней; `/me/permissions`
отдаёт эффективные права + `granted`. Пустая таблица = поведение
идентично текущему (регресс не возможен).
Приёмка: pytest — max(роль, личная) на всех уровнях, доступ появляется
без перелогина, API-токены ходят по роли токена; smoke + ruff зелёные.

**B. API делегирования + каскад + анти-эскалация.** 4 эндпоинта §6,
аудит + record_versions, каскад при PATCH роли и отзыве, GET /users
расширен.
Приёмка: живой прогон всех сценариев §4 суб-агентом приёмки (особенно:
403 на чужой модуль, 403 у ro-выдающего, каскад после смены роли);
pytest-блок `test_delegation.py` (все §4 как код); ruff.

**C. UI.** Вкладка «Пользователи» (§7): выдача/отзыв для не-admin,
полная картина для admin, «Нет доступных модулей» для чисто-ro.
Приёмка: браузером — руководитель без crm не видит crm в выдаче и не
может его вписать (клиент — удобство, сервер уже защищён); выдача из UI
видна в журнале events_log; vue-tsc/build; i18n-ключи; пересборка web.

## 9. Что НЕ входит в эту версию (v1)

- Оргдрево, отделы, подчинённость, «сферы» как сущности — v2+.
- Понижение доступа ниже роли (личное `none` не перекрывает `role rw`) —
  осознанная граница: надстройка только добавляет; понизить — сменить
  роль у админа.
- Сроки действия выдач, лимиты числа выдач, согласования (approval) — v2+.
- Делегирование создания/деактивации пользователей (рекомендация Р3 —
  admin-only).
- Права внутри модуля (тоньше rw/ro/none) — не поднимаем.
- Личные выдачи для API-токенов; массовые операции; UI-отчёт «цепочка
  делегирования» (читается из events_log/record_versions руками).
- События делегирования в шину (outbox).

## 10. Профили конфигураций (без реализации — рецепты настройки)

- **МСБ (до ~15 чел)**: admin = гендир; хватает ролей-пресетов и 1–2
  выдач (например, бухгалтеру — accounting, продавцу — crm). Делегирование
  почти не используется — это нормально, ничего настраивать не нужно.
- **Средний (15–100)**: admin делегирует руководителям направлений rw в
  их сферах (учёт / продажи / интеграции); те сами наделяют отделы и
  работников. Покрывается v1 полностью.
- **Крупный (100+)**: нужны оргдрево, области делегирования как сущности,
  лимиты, согласования, сроки — v2+ (эта спека — фундамент: `granted_by`
  и каскад переживут появление оргдрева).

## 11. Открытые вопросы (развилки, с рекомендациями)

- **Р1. Модель: `user_permissions` (надстройка) vs роли-с-владельцем.**
  Второй вариант — руководитель создаёт роли-срезы («бухгалтерия отдела»),
  владелец назначает их. Минусы: у пользователя одна роль (`models.py:29`)
  — нужны составные роли под каждую комбинацию модулей; роли глобальны,
  «владение» ломает матрицу и семантику admin-only; анти-эскалация —
  сверка матрицы роли с правами выдающего на каждый назначающий вызов.
  Рекомендация: **`user_permissions`** (принято в §5); роли-с-владельцем
  вернуть к v2, если понадобятся именованные наборы.
- **Р2. Каскад при потере собственных прав: немедленный vs ленивый.**
  Ленивый (строки живут, новые выдачи блокируются) — тише, но доступ
  «висит в воздухе» и отзыв растянут во времени — небезопасно.
  Рекомендация: **немедленный рекурсивный каскад** в той же транзакции
  (§4); в масштабе МСБ дёшево, путь роста — фоновая джоба при >1000 строк.
- **Р3. Кто создаёт пользователей — ПЕРЕОТКРЫТО И РЕШЕНО основателем
  2026-09-11 (см. §12).** Руководитель (обладатель rw хотя бы на один
  модуль) МОЖЕТ создавать учётки — но всегда «пустые» (без ролей, без
  доступа к функционалу: экран «Нет доступа» уже работает); функционал
  появляется только при первой выдаче прав, которая генерирует
  временный пароль. Логин генерируется системой из ФИО. Детали — §12.
  Удаление учёток — по-прежнему admin-only.
- **Р4. Отображение в матрице «Доступы и роли».** Матрица остаётся
  ролями; личные выдачи: (а) отдельной вкладкой «Пользователи» рядом
  (рекомендация — сделано в §7), (б) колонкой в матрице — ломает макет,
  (в) только журнал — непригодно для рутины. Админ видит признак
  «личное» в карточке пользователя, чтобы не искать расхождение
  роль/факт руками.
- **Р5. Понижение ниже роли.** Требует семантики приоритета личного над
  ролевым (и решения, что делать при конфликте с каскадом). Рекомендация:
  осознанно вне v1 (§9); вернуться, если у пилотов появится запрос
  «работник уволился с должности, но остался в системе».

## 12. Жизненный цикл учётки (дополнение основателя 2026-09-11, включено в v1)

Видение основателя: админ/руководитель создаёт учётку из настроек
(окно контактных данных), логин генерирует система из ФИО, доступ к
функционалу появляется только при первой выдаче ролей — вместе с
временным паролем, который пользователь обязан сменить за 3 дня.

1. **Создание учётки**: право — admin ИЛИ обладатель rw хотя бы на один
   модуль; окно заполняет ФИО + email + телефон. Учётка создаётся
   **пустой** (без роли и прав) — при входе пользователь видит
   существующий экран «Нет доступа» (функционал недоступен, ровно по
   видению: доступ появляется только с ролями).
2. **Логин из ФИО**: транслитерация, шаблон «инициалы+фамилия» без
   разделителей, верхний регистр (Иван Иванович Иванов → IIIVANOV);
   уникальность — при совпадении числовой суффикс: IIIVANOV1, IIIVANOV2
   (индекс = первый свободный). Колонка `users.username` (UNIQUE),
   вход принимает **username ИЛИ email** (модель аутентификации не
   меняется, email остаётся контактом для восстановления).
3. **Первая выдача прав = активация**: при первой выдаче (роль от
   админа или личное право от руководителя) система предлагает
   «сформировать временный пароль» (окно подтверждения); пароль
   генерируется по существующей парольной политике и показывается
   **один раз** создателю (передаётся пользователю вне системы).
4. **3 дня на смену**: у учётки с временным паролем дедлайн
   `must_change_password_by = +72ч` (расширение существующего флага
   must_change_password в /auth/me). До смены: каждый экран
   напоминает баннером; мутации (POST/PATCH/DELETE любых модулей) —
   403 `password_expired` после истечения дедлайна (чтение доступно,
   чтобы войти и сменить пароль всегда можно). Смена пароля снимает
   флаг и дедлайн.
5. Аудит: создание учётки, генерация временного пароля (факт, без
   значения), первая выдача прав — AuditEvent.

Этапы не меняются: механика §12 входит в этап A (модель+username+
дедлайн) и этап C (UI: окно создания с автогенерацией логина —
предпросмотр логина до сохранения; окно подтверждения временного
пароля при первой выдаче; баннер-напоминание).

## 16. Координация с мультитенантностью (дополнение 2026-09-14)

Реализация мультитенантности (multitenancy-spec §10 A–D) завершена ДО
делегирования (как решено в развилке О3). Все таблицы и проверки
делегирования работают в контексте организации из JWT (CompanyScoped):

- `user_permissions` — гранты в пределах ОДНОЙ организации: выдающий
  и получатель обязаны быть в одной org (проверка при выдаче; чужая
  org → 404).
- `effective_module_level(db, user, module)` — не меняется, поверх
  роли и личных грантов; org-фильтр данных — отдельным CompanyScoped
  (как в B1–B3), делегирование не дублирует.
- Каскад при смене роли — в пределах организации пользователя.
- Супер-админ платформы (is_platform_admin) — вне делегирования
  (платформенный контекст, не бизнес-модули).
- Создание учёток (§12): «пустые» — company_id наследуется от
  создателя (уже реализовано в этапе A); username из ФИО и временный
  пароль при первой выдаче — без изменений.
