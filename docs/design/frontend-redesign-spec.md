# Спека: редизайн фронтенда — дизайн-система «Квазар», экраны модулей, роли

Статус: готова к разработке · Дата: 2026-09-03 · Чат: архитектурный

## 1. Контекст и цель

Бэкенд готов (ядро, интеграции, учёт, ИИ, CRM — 5 схем, 39 таблиц, ~65
pytest, smoke зелёный). Текущий фронтенд — каркас на Element Plus с шестью
экранами (вход, подключения, синхронизации, система, уведомления,
ассистент); экраны учёта и CRM отсутствовали by design («после готовности
бэкенда»). Основатель принял дизайн макета (демо-организация в нём —
«ТехноПром», не бренд продукта) как
источник истины: текущий вид «отдаёт ИИ» и отталкивает пользователей.

Решения (реестр 2026-09-03):

- **Стек не меняем**: Vue 3 + Vite + TS + Pinia остаётся. Берём визуальный
  дизайн макета, техническая реализация наша. React-код макета в сборку
  не входит — только эталон для сверки.
- **Element Plus убираем** поэтапно, заменяем собственной мини-библиотекой
  компонентов в стиле макета.
- **Гранулярные роли** (роль → права на модуль) поднимаются из
  security-plan P2 в эту спеку: без них навигацию «видит только своё»
  не построить.
- Операционные домены (склад и др.) — по ADR-007, их экраны добавятся
  после появления бэкенда; в v1 их в меню нет (не заглушки).

## 3. Дизайн-токены

Переносим `globals.css` макета в `frontend/src/styles/tokens.css` как есть
(полный файл — эталон; ниже ключевые значения):

- Радиус: `--radius: 0.625rem` (10px), производные sm/md/lg/xl.
- Акцент бренда: **emerald-500** (логотип, активный пункт меню, кнопки
  действий, положительная дельта). Сайдбар всегда тёмный `zinc-900`,
  рабочая зона — светлая `--background: oklch(1 0 0)`.
- Статусные бейджи (из `shared.tsx` макета): новый — sky, в работе —
  amber, отгрузка — teal, выполнен — emerald, отменён/просрочен — red,
  черновик — zinc. Каждый бейдж: светлая и тёмная пара классов.
- Тёмная тема: класс `.dark` на `<html>`, переключатель в шапке, выбор
  хранится в localStorage, переход 0.25s. Каждое состояние каждого
  компонента обязано иметь тёмную пару (стр. 11–12 макета — эталон).
- Анимации: появление строк 0.28s, экрана 0.22s; всё гасится при
  `prefers-reduced-motion: reduce`.
- Скроллбар: тонкий 6px, стиль `.erp-scroll` из макета.

Источники подключений (ADR-001 — ничего с CDN):

- Шрифты Geist Sans / Geist Mono — локально через `@fontsource`
  (woff2 в бандле); если пакета нет в npm — файлы положить в
  `src/assets/fonts/` и подключить через `@font-face`. Fallback:
  `system-ui, -apple-system, sans-serif`.
- Иконки — `lucide-vue-next` (те же имена, что в макете).
- Tailwind CSS v4 через `@tailwindcss/vite` + `@theme inline` маппинг
  токенов (как в `globals.css` эталона).

## 6. Роли и права

### 6.1 Модель данных (erp_core)

- Таблица `roles`: `key` (text, PK — 'admin' | 'user' | 'readonly' |
  кастомные), `name`, `description`, `is_builtin` (bool).
- Таблица `role_permissions`: `(role_key, module)` PK, `level` text
  ('rw' | 'ro'). Отсутствие строки = доступ закрыт ('none').
- `users.role` остаётся текстовым ключом, добавляется FK на `roles.key`.
- Миграция засеивает builtin-роли матрицей, эквивалентной текущему
  поведению (ничего не должно сломаться):
  - `admin` — rw везде, в UI помечена замком (неизменяемая);
  - `user` — rw: accounting, crm, integrations, ai; ro: system;
  - `readonly` — ro везде.
- Кастомные роли создаёт админ (POST /roles): ключ генерируется из
  названия (slug), `is_builtin = false`.

### 6.2 API

- `GET /api/v1/me/permissions` → `{ role: {key, name}, permissions:
  {accounting: 'rw', crm: 'ro', integrations: 'none', ai: 'rw',
  system: 'ro'} }` — любой аутентифицированный пользователь.
- `GET /api/v1/roles` (admin) → роли с правами и числом пользователей.
- `PUT /api/v1/roles/{key}/permissions` (admin) — вся матрица роли разом;
  для `admin` — 400 «неизменяемая роль».
- `POST /api/v1/roles` / `DELETE /api/v1/roles/{key}` (admin; удалять
  можно только роль без пользователей).
- Модули матрицы: `accounting`, `crm`, `integrations`, `ai`, `system`.

### 6.3 Enforcement

- В ядре — зависимость `require_module(module, level)`:
  level 'ro' — доступны GET, 'rw' — всё; 'none'/нет строки — 403.
  Проверка по роли пользователя из БД (кэш на 60с допустим, инвалидация
  при PUT прав не критична — «применится в течение минуты»).
- Модули мигрируют с `WriteUser`/`CurrentUser` на `require_module`
  поэтапно, вместе со своими экранами (этапы D/E/F/G): accounting →
  `require_module('accounting', …)`, crm → `('crm', …)`, интеграции и
  система → свои, ассистент → `('ai', …)`. Тесты 403/200 — как делали
  для readonly в test_security.py.
- UI: навигация строится из `/me/permissions` (пункт виден, если уровень
  ≠ none), роут-гард сверяет `meta.module` + `meta.level`, запрещённый
  URL → редирект на первый доступный раздел. Скрытие в UI — удобство,
  защита — сервер.

### 6.4 Экран «Доступы и роли» (Настройки)

Точная копия `PermissionsMatrix` из макета: карточки ролей (цвет, имя,
описание, число сотрудников), матрица роли × модули, клик по ячейке
циклит `rw → ro → none`, кнопка «Применить права» активна при изменениях,
легенда R/W · R/O · — · 🔒 admin. Плюс кнопка «Новая роль» (диалог:
название, описание → POST → строка в матрице).

## 8. Этапы

Каждый этап = отдельный коммит(ы) + пересборка `docker compose build web`
(урок из vue-tsc `put`: любое изменение в `frontend/**` требует пересборки
образа). Приёмка здесь: ручная сверка с PDF-эталоном + smoke + pytest
(для этапов с бэкендом) + ruff.

**A. Фундамент.** Tailwind v4 + токены, шрифты, иконки, ui-библиотека
(§4), ErpShell с навигацией и темами, роуты-редиректы, старые экраны
живут внутри новой оболочки на Element Plus.
Приёмка: сходство каркаса со стр. 3/11 макета; обе темы; центр
уведомлений §5.1 (реальные события, счётчик, фильтры, переходы);
`<title>Квазар`
(одновременно обновить проверку в `tests/smoke.py`, строки с
`<title>ERP</title>`) и `/assets/` в smoke; в бандле нет внешних URL
(grep по dist на `http` кроме /api); vue-tsc/build зелёные; i18n-ключи
для всех новых строк.

**B. Вход.** LoginView по стр. 2: сплит, слева бренд-панель Квазара
(логотип-«К», имя продукта, слоган), справа форма (email, пароль,
«Запомнить», ошибка 401/429 с таймером блокировки), задел поля 2FA.
Приёмка: вход/выход/refresh работают как раньше; редирект по правам;
блокировка после 5 попыток отражается в UI.

**C. Роли (бэкенд + матрица).** Миграция §6.1, API §6.2,
`require_module` §6.3, экран матрицы §6.4 (временно в разделе Настройки
на старом SystemView-каркасе — переносится в G), фильтрация навигации.
Приёмка: pytest на 403/200 по уровням; e2e: пользователю с `crm: none`
раздел не виден, прямой URL → редирект; PUT прав меняет доступ в
течение минуты без перелогина.

**D. Финансы.** FinanceView по стр. 7 (§7, строка «Финансы»), полный
CRUD + сторно + заморозка курса в диалоге создания, суммы строками
Decimal через `utils/money.ts`, переключение периода.
Приёмка: создание/сторнирование транзакции через UI отражается в API;
формат сумм как в учёте (4 знака из API — отображение 2);
сторно-запись видна; enforcement `require_module('accounting')` на
эндпоинтах модуля.

**E. Продажи (CRM).** Список сделок (стр. 4) + карточка (стр. 5) +
печать карточки (минимум по стр. 6). Смена стадии drag-не-обязательна
(клик/меню достаточно; канбан с dnd — этап H).
Приёмка: цикл сделки новый → won с соблюдением move-правил;
коммуникация/задача создаются и видны в таймлайне; история изменений
открывается; enforcement `require_module('crm')`.

**F. Дашборд и отчёты.** Стр. 3 и 10 (§7). KPI и графики из наших API,
клик по KPI ведёт в раздел. Экспорт 1C — кнопка скачивания файла.
Приёмка: числа KPI совпадают с ручным вызовом API; график ДДС строится
по дням/неделям; пустые данные — EmptyState, не пустые карточки.

**G. Система.** Настройки (организация, профиль+пароль, безопасность,
доступы и роли — финальный дом матрицы, бэкапы, обновления, журнал),
Интеграции (подключения, синхронизации, вебхуки/рецепты, правила
уведомлений — переприход всех старых экранов), ИИ-ассистент в новом
дизайне (чаты, документы, предложения с подтвердить/отклонить).
Удаление Element Plus.
Приёмка: вся старая функциональность доступна в новом облике (чеклист
по экранам); grep `el-` = 0; enforcement integrations/system/ai.

**I. Ресурсы** (после готовности бэкенда по
`docs/design/resources-core-spec.md`): номенклатура, склады/остатки/
движения, закупки, продажи-документы, сборка — по страницам макета
«Заказы» (стр. 4), «Карточка заказа» (стр. 5), «Склад» (стр. 8);
цифровые товары — те же экраны, локации kind=digital. Сроки и состав —
отдельным решением после приёмки бэкенда ресурсов.

**H. Бэклог (отдельные решения по каждому).** Командная палитра Ctrl+K,
центр уведомлений — серверная версия (персистентность прочитанного,
бизнес-события), канбан с drag-n-drop, печатные формы документов,
доводка мобильного вида, конструктор отчётов.

## 9. Правила разработки

- i18n: все пользовательские строки — ключи ru/en с первого дня экрана.
- Деньги: только строки Decimal с сервера; отображение — `utils/money.ts`;
  арифметика в UI — запрещена (кроме отображаемых дельт от API).
- ADR-001: шрифты/иконки в бандле; в dist нет внешних URL.
- ADR-002: фронтенд толерантен к добавлению полей в payload.
- Этапы не смешивать; после каждого — пересборка web и smoke.
- React-эталон не копировать в `src/` ни частично.

## 10. Non-goals v1

Экраны Склада и Персонала (нет бэкенда), Торг-12 и конструктор печатных
форм, конструктор отчётов, командная палитра, центр уведомлений, канбан
с dnd, 2FA (P1; только задел поля), мультитенантность.
