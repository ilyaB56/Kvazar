# Спека: ядро управления ресурсами (НСИ, склад/цифровой учёт, закупки, продажи, сборка)

Статус: готова к разработке (развилки закрыты основателем 2026-09-04,
см. §11) · Дата: 2026-09-04 · Чат: архитектурный

## 1. Контекст и решения основателя

Диагноз основателя: в системе нет главного, ради чего покупают ERP —
управления ресурсами. Есть деньги (mgmt_accounting), воронка (mini_crm),
интеграции, ИИ. Решения основателя (2026-09-04):

1. Пилоты: и те, у кого физические склады (деньги учитывают тоже), и
   **продавцы цифровых продуктов** (подписки, игры, коды пополнения).
   Цифровой «склад» — таблицы в нашей БД: товар поступает в базу данных,
   а не в помещение.
2. Блоки: (а) складской/цифровой учёт движений товаров по складам;
   (б) учёт закупок — что и на сколько закуплено; (в) управленческий учёт
   доходов/расходов по статьям — **уже реализован** (mgmt_accounting).
3. Производство-сборка и перепродажа (цифровых и материальных) — нужны.
4. Порядок работ: сначала бэкенд ресурсов, экраны — потом (этап I
   редизайна).

Архитектурный дом — **ADR-007**: все фичи-подпакеты внутри модуля
`mgmt_accounting` (`features/{nsi, inventory, purchasing, sales,
production}`), общая схема БД, общие транзакции с деньгами.

Реализационные паттерны заимствуем у проверенных систем (обсуждали
2026-09-04): двойная запись движений между локациями — Odoo Inventory;
«документ → проводки», заказы с частичными исполнениями — 1С/МойСклад;
средняя себестоимость — стандарт МойСклад/1С.

## 2. Ключевые принципы

1. **Единая механика для физических и цифровых товаров** — различие
   только в типе локации и способе учёта единиц (количеством или
   поэкземплярно). Цифровой товар = номенклатура `kind=digital` +
   «склад» `kind=digital`; каждая единица — уникальный код
   (серийник). Отгрузка цифрового = выдача конкретного кода.
2. **Двойная запись движений** (как в деньгах): каждое движение товара —
   строка `from_location → to_location`. Остаток локации = Σ входов −
   Σ выходов. Товар не возникает из ниоткуда и не исчезает в никуда:
   приход = `Поставщик(транзит) → Склад`, расход = `Склад →
   Клиент(транзит)`, списание = `Склад → Брак`, сборка = компоненты
   `Склад → Производство(транзит)`, продукция `Производство → Склад`.
   Транзитные локации неснижаемые (нет своего остатка, только в потоке).
3. **Документ → проводки**: заказы/приёмки/отгрузки/сборки — документы
   со статусами и номерами по doc_sequences (механизм уже есть в
   модуле). Проведение документа создаёт движения и/или платежи.
   Непроведённый документ ничего не меняет (черновик).
4. **Одна транзакция БД** на проведение: приёмка = документ + движения +
   пересчёт средней себестоимости; оплата = платёж + связка с заказом.
   Это прямое следствие единой схемы (ADR-007).
5. **Деньги и товары связываются через документы**: платежи ссылаются на
   заказ, статьи «Закупки товаров»/«Продажи» аватар-создаются в
   категориях учёта, контрагент наследуется.
6. Мультивалютность — по ADR-003: валютная цена заказа + замороженный
   курс на момент создания документа; себестоимость всегда в базовой
   валюте (RUB).
7. UI — не в этой спеке (этап I редизайна); всё через API, как делали
   для CRM.

## 3. Модель данных (схема mgmt_accounting, Alembic-миграция модуля)

### 3.1 НСИ

- `items` — номенклатура: `id, sku (уникальный артикул), name, kind
  (physical | digital | service), unit_code (шт/кг/час/лицензия…),
  tracking (qty | serial), barcode, sale_price NUMERIC(20,4) в базовой
  валюте (прайсы-списки — v2), is_active, ts-поля`. Услуга
  (`service`) не имеет движений вообще — только строки заказов и деньги.
- `units` — справочник единиц (seed: шт, кг, л, м, час, мес, лицензия).
- Средняя себестоимость — `avg_cost NUMERIC(20,4)` на item (см. §4).

### 3.2 Склады и движения

- `locations` — `id, name, kind (physical | digital), is_transit
  (bool), is_active`. Seed: «Основной склад» (physical), «Цифровой
  склад» (digital), транзитные системные `Поставщик`, `Клиент`,
  `Производство`, `Брак` (не редактируются, kind по умолчанию
  physical — совместимость определяется по товару).
- `stock_moves` — `id, item_id, qty NUMERIC(20,4) > 0, unit_cost
  NUMERIC(20,4) (базовая валюта; NULL у расходных записей — несут
  себестоимость отдельно), from_location_id, to_location_id,
  counterparty_id (кто источник/получатель, для транзитных),
  source_type + source_id (документ), moved_at, created_by, note`.
  Индексы: (item, location), (moved_at).
- `item_serials` — поэкземплярный учёт цифровых: `id, item_id, code
  (уникальный, хранить **Fernet-шифрованным** — коды пополнения = актив),
  status (in_stock | reserved | sold | void), location_id, unit_cost,
  received_at (из какой приёмки), sold_move_id`. Движение серийного
  товара всегда qty=1 и связано с конкретным серийником.
- Остатки — представление `v_stock_balances` (item × location ×
  qty × avg_cost × стоимость) поверх движений; на дату — запросом.
  Материализация — при миллионах строк (v2).

Совместимость: физический товар — только по физическим локациям,
цифровой — только по цифровым; нарушение — 422.

### 3.3 Закупки

- `purchase_orders`: `id, number (doc_sequences, тип «Заказ
  поставщику»), counterparty_id, status (draft | confirmed |
  partially_received | received | closed | cancelled), currency +
  frozen_rate (ADR-003), amount / amount_base, note, ts, created_by`.
- `purchase_order_lines`: `order_id, item_id, qty, unit_price (в валюте
  заказа), amount`.
- `receipts` (приёмки): `id, number, purchase_order_id (nullable —
  можно без заказа), counterparty_id, status (draft | posted),
  counterparty_doc (номер накладной поставщика), ts`. Строки
  `receipt_lines`: `item_id, qty, unit_cost (в базовой валюте; для
  валютной закупки — пересчёт по frozen_rate), serial_codes (для
  serial-товаров: список кодов, qty = len)`.
- Проведение приёмки: движения `Поставщик → локация` + серийники +
  пересчёт avg_cost + статус заказа (частично/полностью) + событие.
- Оплата закупки: исходящая `transaction` (существующая таблица) с
  `source_type='purchase_order'`, категория «Закупки товаров»
  (авто-создание seed-категории при первой оплате), контрагент
  наследуется. Частичные оплаты — просто несколько транзакций.

### 3.4 Продажи

- `sales_orders`: `id, number («Заказ клиента»), counterparty_id,
  crm_deal_id (nullable — связь со сделкой), status (draft | confirmed |
  partially_shipped | shipped | closed | cancelled), currency +
  frozen_rate, amount/amount_base, ts, created_by`.
- `sales_order_lines`: item, qty, unit_price.
- `shipments` (отгрузки): `number («Отгрузка»), sales_order_id,
  status (draft | posted)`; строки: `item, qty, serial_codes (для
  цифровых — какие коды выдать; по умолчанию FIFO-автовыбор)`.
- Проведение отгрузки: контроль остатка (по умолчанию запрет минуса,
  настройка модуля `allow_negative_stock=false`), движения `локация →
  Клиент`, серийники → sold, списание себестоимости, статус заказа,
  событие.
- Оплата: входящая transaction, категория «Продажи», source-ссылка.
- Резерв v1 — статус строки заказа (`reserved_qty` на строке,
  уменьшает «доступный остаток» = баланс − резервы); жёсткая
  блокировка и резерв по сроку — v2.
- Связь с CRM: событие `crm.deal.won` (уже существует) → в карточке
  сделки кнопка «Создать заказ» (UI этап I; API принимает `deal_id` и
  префиллит контрагента). Автосоздание — настройка, выкл. по умолчанию.

### 3.5 Сборка (простое производство)

- `tech_cards` (спецификации): `id, product_item_id, qty_out,
  components (jsonb: [{item_id, qty}]), is_active`. Одноуровневые.
- `production_orders`: `number («Сборка»), tech_card_id, qty_planned,
  status (draft | posted | cancelled)`. Проведение: списание компонентов
  `Склад → Производство` по средней, оприходование продукции
  `Производство → Склад` по себестоимости материалов (+ нетрудозатраты:
  labour cost — v2), событие. Частичное — v2.

### 3.6 Отчёты (read-only API)

- Остатки на дату (по складам/товарам, стоимость по avg_cost).
- Журнал движений (фильтры: период, товар, склад, контрагент, документ).
- Закупки за период: Σ по заказам/приёмкам, по товарам, по поставщикам.
- Продажи за период: Σ, маржа = продажи − себестоимость списаний.
- Взаиморасчёты: сальдо по контрагенту = (оплаты закупок − приёмки)
  и (заказы продаж − оплаты), детализация по документам.

## 4. Себестоимость

Средняя взвешенная per item (решение-кандидат, §11.2):

- Приход: `avg_cost_new = (qty_rest × avg_cost + qty_in × unit_cost) /
  (qty_rest + qty_in)` — пересчёт атомарно в транзакции приёмки.
- Расход/сборка: списание по текущей avg_cost; unit_cost расходного
  движения = avg_cost на момент.
- Инвентаризация: излишек по avg_cost, недостача списывает по avg_cost.
- Отрицательный остаток запрещён (кроме настройки allow_negative) —
  avg_cost при нуле = цена последнего прихода.

## 5. События (шина, контракты по ADR-002)

`acc.purchase.order.created|confirmed`, `acc.purchase.received`,
`acc.sales.order.created|confirmed|shipped`,
`acc.inventory.stock_changed` (batch: item, location, qty_delta),
`acc.inventory.low_stock` (порог на item, проверка при проведении),
`acc.production.order.posted`. Payload: деньги строками (Decimal),
количества строками. Telegram-белый список дополнить этими ключами.

## 6. API (под url_prefix /api/v1/accounting, требования ролей как в модуле)

НСИ: `GET/POST /items`, `GET/PUT/DELETE /items/{id}` (DELETE — только
неактивную, движений нет); `GET /units`.
Склад: `GET/POST /locations`; `GET /stock/balances?on_date=&location=`;
`GET /stock/moves?…`; `POST /stock/transfer` (перемещение);
`POST /stock/adjustment` (инвентаризация: локация, строки факт).
Закупки: `GET/POST /purchase-orders`, `GET /purchase-orders/{id}`,
`POST …/{id}/confirm|cancel`; `GET/POST /receipts`, `POST
/receipts/{id}/post|unpost` (unpost — только без последующих движений;
сторно-механика как в транзакциях).
Продажи: зеркально `/sales-orders`, `/shipments`.
Сборка: `GET/POST /tech-cards`, `GET/POST /production-orders`,
`POST /production-orders/{id}/post`.
Отчёты: `GET /reports/purchases|sales|stock|counterparty-balance`.
Валидация 422 с человекочитаемыми кодами ошибок (insufficient_stock,
serial_not_found, kind_mismatch…).

## 7. Этапы

- **A. НСИ + склад-ядро**: items/units/locations/stock_moves/
  item_serials (таблицы+seed), v_stock_balances, перемещение,
  ручное оприходование/списание (adjustment), avg_cost, отчёт остатков,
  события stock_changed/low_stock. Приёмка: pytest (двойная запись,
  совместимость видов, серийники, средняя), smoke-секция.
- **B. Закупки**: заказы + приёмки + оплаты + отчёты закупок +
  взаиморасчёты поставщиков. Приёмка: полный цикл с частичной приёмкой,
  валютная закупка с заморозкой курса, сторно приёмки.
- **C. Продажи**: заказы + отгрузки + оплаты + маржа + связь со сделкой
  CRM (`crm_deal_id`) + события. Приёмка: цикл заказ → частичные
  отгрузки → оплата; продажа цифровых (выдача кодов FIFO);
  контроль минуса; сделка won → черновик заказа.
- **D. Сборка**: тех.карты + заказы на сборку + события. Приёмка:
  списание материалов, приход продукции, себестоимость продукции =
  материалы.
- **E. Полировка**: unpost-правила, лимиты истории (record_versions на
  документы — версионирование уже есть в ядре), Telegram-белый список,
  OpenAPI-примеры, README-раздел «ресурсы».

Каждый этап — отдельный коммит; миграции обратимые; ruff/pytest/smoke
зелёные; изменение схемы — через Alembic цепочку модуля.

## 8. Права доступа

Все эндпоинты — в модуле mgmt_accounting → матрица ролей действует
как есть (`accounting` rw/ro/none; readonly видит отчёты и остатки,
не проводит). После этапа C редизайна — переход на
`require_module('accounting', level)` из спеки редизайна §6.3.

## 9. Что сознательно не делаем в v1

Партии/сроки годности, FIFO/LIFO, прайс-листы и скидочные политики,
многоуровневые BOM, трудозатраты в себестоимости, резерв с датой
снятия, ячейки внутри складов, штрихкод-сканирование, возвраты
поставщикам/от клиентов (v2 — через отрицательные документы),
регл. учёт (принципиально, навсегда — кормим 1С).

## 10. Связь с другими спеками

- Редизайн фронтенда: экраны ресурсов — этап I (страницы макета
  «Заказы», «Карточка заказа», «Склад»), после этого бэкенда.
- Обновления/бэкапы: новые таблицы наследуют общий механизм.
- ИИ-ассистент: read-only инструменты (остатки, закупки за период)
  добавить после этапа C (отдельная задача).

## 11. Развилки — РЕШЕНЫ основателем 2026-09-04

1. **Хранение цифровых кодов**: хранить в БД, **Fernet-шифрованными**
   (рекомендация принята; ключ — существующий SECRETS_KEY, как у
   credentials интеграций). Открытым текстом — только отдельным
   решением основателя.
2. **Себестоимость**: **средняя взвешенная** (§4). FIFO — v2+.
3. **Взаиморасчёты**: **лёгкие** — платежи привязываются к заказам,
   сальдо по контрагенту считается запросом (§3.6). Полный учёт
   задолженностей — v2+.
4. **Контроль минуса**: отгрузка сверх остатка **запрещена** по
   умолчанию; глобальная настройка `allow_negative_stock=false` в
   erp_core settings — можно отключить (API настроек + переключатель в
   UI на этапе I). При выключенном контроле расход по минусовому
   остатку списывается по последней avg_cost.
