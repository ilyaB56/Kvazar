# Спека: контроль одновременных сеансов (безопасность входа)

Статус: к утверждению основателем · Дата: 2026-09-11 · Чат:
архитектурный (фокус «безопасность», отзыв основателя 2026-09-11)

## 1. Контекст и задача

Отзыв основателя: при входе система должна проверять, первый ли это
заход; если пользователь уже вошёл и не вышел — показать окно
«в учётку уже зашли» с выбором: **выйти из всех сессий** или
**продолжить, не выходя из текущих**.

Сегодня пары access+refresh с jti/ver и `revoked_tokens` есть, но
понятия «активный сеанс» как сущности нет: нельзя ответить «сколько
живых входов у пользователя» и нельзя выборочно завершить чужие.

## 2. Решение

### 2.1 Сущность сеанса (erp_core.auth_sessions)

| колонка | тип | примечание |
|---|---|---|
| id (UUID) | PK | = jti refresh-токена |
| user_id | FK users | индекс |
| user_agent | Text | из запроса логина (обрезка 256) |
| ip | String(64) | из запроса логина |
| created_at | ts | момент входа |
| last_used_at | ts | обновляется при /auth/refresh этой сессии |
| revoked_at | ts NULL | отзыв (logout/ротация/logout-others) |

Жизненный цикл: строка создаётся при выдаче refresh; `/auth/logout`
помечает revoked_at (существующая логика отзыва не меняется —
добавляется только пометка); протухший по TTL refresh при рефреше
помечает revoked_at (уборка). «Активный сеанс» = revoked_at IS NULL и
TTL не истёк. Ротация refresh сохраняет id сеанса (jti нового токена
= id строки: refresh ротируется, jti переписывается — либо строка
продлевается с новым jti; принимаем: строка одна, jti обновляется).

### 2.2 API (ядро, /api/v1/auth)

- `POST /login` — ответ дополняется полем `active_sessions: N`
  (количество активных сеансов ПОСЛЕ этого входа, включая текущий).
  Логин всегда успешен — блокировки нет (предупреждение, не запрет).
- `POST /logout-others` `{refresh_token}` — завершить все прочие
  активные сеансы пользователя (текущий, чей токен передан, остаётся);
  ответ `{terminated: N}`. Токен обязателен и валиден — иначе 401.
- `GET /sessions` (CurrentUser) — свои активные сеансы: id,
  user_agent, ip, created_at, last_used_at, текущий помечен
  `is_current` (по jti access-токена).
- `POST /sessions/{id}/revoke` (CurrentUser) — завершить свой сеанс
  (кроме текущего — для текущего есть logout). Возвращает 404/409.

Смена пароля / token_version-bump завершает ВСЕ сеансы (существующее
поведение сохраняется: строки ревокаются каскадно).

### 2.3 UI

- **Модалка при входе**: если `active_sessions > 1` после логина —
  поверх дашборда окно «В аккаунт уже выполнен вход» (+N других
  сеансов): «Завершить другие сеансы» (вызывает logout-others, тост
  «Завершено N») / «Продолжить» (закрыть, оба сеанса живут).
  Показ один раз за вход; не блокирует интерфейс.
- **Экран «Активные сеансы»**: Настройки → Безопасность → список
  (устройство/браузер из user_agent, IP, «вход», «активность»,
  метка «текущий»), кнопка «Завершить» на каждом чужом и «Завершить
  все другие сеансы». i18n ru/en.

### 2.4 Безопасность

- logout-others и revoke принимают только СВОИ сеансы (user_id из
  валидного токена); чужие → 404.
- ip/user_agent — данные для показа самому пользователю; в события
  шины не публикуются; ИИ их не видит (ADR-006). **Ревью 2026-09-11:
  IP = ПОСЛЕДНИЙ адрес X-Forwarded-For** (его дописывает наш nginx,
  равен реальному remote_addr); первый адрес клиент может подделать —
  не доверять (подтверждено инъекцией на приёмке).
- Rate limit логина уже есть (5/60с) — не меняется.

## 3. Этапы

- **A. Бэкенд**: миграция auth_sessions; запись при login; revoked при
  logout/ротации; active_sessions в ответе логина; /logout-others,
  /sessions, /sessions/{id}/revoke; last_used_at при refresh. Тесты:
  двойной вход → active_sessions=2; logout-others → остаётся 1;
  revoke чужого → 404; смена пароля → все сеансы завершены.
- **B. UI**: модалка входа (по active_sessions>1), экран активных
  сеансов в Безопасности, i18n. Приёмка: живой вход в двух браузерах
  (или обычный + приватный) → модалка; «завершить другие» → первый
  браузер получает 401 на действии/refresh и уходит на логин.

## 4. Non-goals v1

Привязка устройства/2FA-push, геолокация IP, лимит числа сеансов,
уведомление в Telegram о новом входе (кандидат P1: notification_rule
на событие auth.session.created), «запомнить это устройство».
