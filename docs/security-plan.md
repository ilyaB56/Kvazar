# План безопасности ERP

Утверждён в архитектурном чате 2026-08-21. Живой документ: пункты
переносятся в задачи разработки по мере приоритета. Источник правил:
ADR-001 (сеть), настоящий план.

## Что уже сделано (сильная сторона)

- JWT (access + refresh), пароли bcrypt; роли admin/user/readonly.
- Аудит-трейл: `erp_core.events_log` (действия) + `erp_core.record_versions`
  (версии записей) — «кто, что, когда» по любому изменению.
- Секреты подключений — Fernet-шифрование; webhook'и — токены + HMAC.
- ADR-001: сеть только через коннекторы; enforced линтером (TID251).
- Нет внешних CDN; CORS настроен; SQL только через ORM (инъекции закрыты).
- `.env` в .gitignore, секреты не в git; обратимые миграции.

## Модель угроз (кратко)

| Кто | Вектор | Что защищает |
|---|---|---|
| Внешний из интернета | подбор пароля, атака на публичные hooks, MITM | HTTPS, rate limit, токены hooks |
| Пользователь внутри | действия вне роли (readonly пишет, user закрывает период) | RBAC-enforce, аудит |
| Утечка носителя/бэкапа | копия БД ушла наружу | шифрование бэкапов, Fernet-секреты |
| Компрометация клиента-«коробки» | подмена обновления | подписи пакетов (Ed25519) |
| Своя ошибка | ключи/секреты в логах и git | политика логирования, .gitignore |

## Бэклог

### P0 — до передачи системы первым внешним пользователям

1. **Enforce readonly-роли** *(найдено на ревью 2026-08-21)*: роль объявлена,
   но не enforced — readonly сейчас может создавать/проводить транзакции.
   Все mutating-эндпоинты должны требовать `require_role("admin", "user")`,
   readonly — только GET. — ✅ **Выполнено 2026-08-22**: алиасы
   `WriteUser`/`AdminUser` (`src/core/auth.py`) на всех мутирующих
   эндпоинтах; проверяется тестами `tests/test_security.py`.
2. **HTTPS**: терминировать на nginx (сервис `web`); для коробки — инструкция
   по сертификатам (self-signed / Let's Encrypt); HSTS. В прод-профиле не
   публиковать порт 8000 api наружу (только через web-прокси).
3. **Brute-force на логине**: rate limit `/auth/login` (напр., 5 попыток/мин
   на IP; nginx `limit_req` + пауза), сообщение без раскрытия, что именно
   неверно (уже так).
4. **Отзыв сессий**: «версия токена» в `users` — смена пароля и «выйти со всех
   устройств» инвалидируют refresh; logout отзывает текущий refresh.
5. **Парольная политика**: минимум 8 символов (есть), запрет топ-1000 частых
   паролей; предупреждение о смене seed-пароля админа при первом входе.
   — Частично: seed-пароль задаётся `SEED_ADMIN_PASSWORD` (2026-08-22);
   blacklist частых паролей и предупреждение при первом входе — открыто.

### P1 — до первых платящих клиентов

6. **2FA (TOTP)**: для admin — обязательно, для остальных — опционально.
7. **Allowlist доменов + журнал исходящих обращений** (хвост ADR-001):
   сейчас коннектор ходит куда угодно; строгий режим — новый домен запрещён
   до явного разрешения; каждый вызов — в журнал (домен, время, статус).
8. **Rate limit на публичные `/hooks/{id}`** (nginx), идемпотентная обработка.
9. **Ротация ключей**: процедура для `JWT_SECRET` (инвалидирует сессии —
   задокументировать как ожидаемое) и `SECRETS_KEY` (скрипт перешифрования
   credentials подключений).
10. **Цепочка поставки**: фиксация версий зависимостей, `pip-audit` и
    `npm audit` в CI; обновления только подписанных пакетов (см. ADR-кандидат
    «Обновления»).
11. **Бэкапы**: шифрование + ежемесячная проверка восстановления
    («непроверенный бэкап — не бэкап»).

### P2 — по мере роста

12. Гранулярные права: роли как набор разрешений (модуль × действие ×
    сущность), а не три фиксированные строки.
13. Файлы-вложения: лимит размера, проверка MIME, хранение вне веб-корня.
14. 152-ФЗ пакет для SaaS: перечень ПДн, хранение в РФ, уведомление РКН,
    политика хранения/удаления, выгрузка ПДн субъекта.
15. Docker-укрепление: контейнеры не от root; сеть — интернет только
    контейнерам интеграционного слоя (профиль «local»).
16. Внешний пентест перед выходом на широкий рынок; регулярный CVE-мониторинг.

## Реагирование на инциденты (минимум)

- Утечка секрета подключения: ротация секрета у провайдера → перешифрование
  → аудит, кто и когда создавал подключение (`record_versions`/`events_log`).
- Утечка `SECRETS_KEY`: скрипт перешифрования по новой версии ключа.
- Компрометация пользователя: смена пароля (инвалидирует refresh) +
  разбор его действий по `events_log`.

## Правила для разработки (добавить к ревью-чек-листу)

- Никаких секретов/паролей в логах и ответах API (маскировать).
- Ошибки авторизации — единый формат 401/403 без деталей внутренностей.
- Новый эндпоинт — явно указать требуемую роль; mutating-логика без роли
  запрещена (по умолчанию — minimum `user`).
- Публичные эндпоинты (hooks) — только через токен/HMAC, с rate limit.
