# ADR-007: Домены операций — фичи внутри модуля учёта, единая база

**Статус:** Принято · **Дата:** 2026-09-03 · **Место решения:** архитектурный чат

## Контекст

Планируются закупки, складской учёт и другие операционные домены.
Требование основателя: единая база данных для всех сфер бизнеса,
не разносить по отдельным модулям. Уточнение: модули системы — это
схемы одной БД PostgreSQL (не отдельные базы), так что «единая база»
уже соблюдена. Вопрос — схема принадлежности и границы новых доменов.

## Решение

1. **Операционные домены (закупки, склад, производство, …) — фичи-подпакеты
   внутри `mgmt_accounting`** (по механике ADR-005):
   `src/modules/mgmt_accounting/features/{purchasing, inventory}/...`
   со своими слоями router/service/models.
2. **Схема БД общая** (`mgmt_accounting`): таблицы товаров, остатков,
   заказов на закупку живут в одной схеме с транзакциями и контрагентами.
   Ключевая выгода — **транзакционная целостность**: проведение платежа и
   движение по складу выполняются в одной транзакции БД (нет распределённых
   согласованностей).
3. Междоменное общение внутри модуля — прямые вызовы service-функций
   (одна схема = один домен); наружу (CRM, ИИ, интеграции) — только события
   шины и публичный API, как раньше (ADR-002 контракты).
4. **Выделение домена в отдельный модуль** допускается только при
   появлении у него собственного жизненного цикла или потребителей вне
   учёта (например, отдельный складской продукт). До этого — рефакторинг
   не делаем.
5. Именование событий новых доменов: `acc.inventory.*`, `acc.purchase.*`
   (префикс домена учёта — единая точка входа для подписчиков).

## Следствия

- Модель данных склада/закупок проектируется в общей схеме; миграции —
  в общую цепочку модуля.
- Событийные контракты (`acc.purchase.order.created`,
  `acc.inventory.stock.changed`, …) фиксируются при проектировании.
- Гранулярные роли (роль → видимость функционала в UI) проектируются
  поверх модульной структуры: разрешение = модуль × действие.
