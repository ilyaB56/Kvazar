# ADR-004: Обновления коробочной версии

**Статус:** Принято · **Дата:** 2026-08-22 · **Место решения:** архитектурный чат

## Контекст

Коробочная версия живёт у клиентов; версии расходятся, клиент обновляется,
когда ему удобно. Обновление должно быть безопасным (данные неприкосновенны),
проверяемым (подпись) и обратимым (откат). Оффлайн-коробка важнее свежести:
предсказуемость важнее автоматизма.

## Решение

### Пакет обновления

- Обновление = **`manifest.json` + подпись Ed25519** поверх него. Манифест:
  версия, канал, дайджесты docker-образов, changelog (RU),
  `min_supported` (минимальная версия, с которой можно обновиться).
- Образы клиент тянет сам из registry; **подпись и дайджесты проверяются
  до скачивания**; непроверяемое — игнорируется с записью в журнал.
- Ключи: приватный — только у нас, офлайн (не на серверах); публичный
  зашит в дистрибутив. Компрометация — перевыпуск ключа в следующем миноре.
  Та же криптография, что лицензии (один механизм).

### Порядок применения (оркестратор `update`)

1. Pre-flight: место на диске, совместимость (`min_supported`), состояние БД.
2. **Обязательный авто-бэкап** (БД + конфиги); минимум три последних
   хранятся, шифрование. *(Бэкапы — предусловие ADR; реализуются этой же
   задачей: расписание 03:00 + внеплановый перед обновлением.)*
3. Загрузка образов с проверкой подписи манифеста и дайджестов.
4. Миграции — транзакционно (DDL в PostgreSQL транзакционен: неудача
   откатывается сама, БД остаётся консистентной на старой версии).
5. Health-check новой версии (`/health` + smoke-проверка ключевых эндпоинтов).
6. Провал health-check — **авто-откат: восстановление бэкапа + прошлый тег
   образов** (старые образы у клиента не удаляются).

### Правила совместимости

- **Откат — только из бэкапа.** `alembic downgrade` на живых данных
  запрещён (даунгрейд поверх изменённых данных = тихая порча);
  downgrade остаётся инструментом разработки.
- Поддержка **N-2** (две последние минорные версии); патчи текущей — без
  ограничений. Прыжки через unsupported-версии — по цепочке.
- Payload событий и `/api/v1` не ломаются внутри минорной версии (ADR-002).

### Каналы и ритм

- `stable` / `beta`. Beta — доступна всем из настроек, с предупреждением,
  без гарантий; подписывается тем же ключом.
- Ритм: минорные ~раз в месяц по готовности (без календарной клятвы),
  патчи — по мере фиксов, beta — еженедельно.
- **Автообновление по умолчанию выключено**: уведомление-pull раз в 24 ч →
  баннер и changelog в админке → кнопка «Обновить» с предупреждением о
  коротком простое. Опция «авто — только патчи» для желающих.

## Следствия

- Задача разработки: оркестратор обновления + система бэкапов (одной
  спекой; бэкапы закрывают и P1 security-plan).
- CI каждого релиза обязан прогонять **upgrade-path тест**: предыдущая
  версия с данными → обновление → smoke (единственная защита от «у нас
  работало»).
- Публикация манифеста — статикой (S3/GH Releases); update-сервер как
  сервис не нужен.
