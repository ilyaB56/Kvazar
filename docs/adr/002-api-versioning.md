# ADR-002: Версионирование API (`/api/v1`)

**Статус:** Принято · **Дата:** 2026-08-18 · **Место решения:** архитектурный чат

## Контекст

Планируются коробочная версия и облачный хаб: версии клиента и хаба будут
расходиться (клиент обновляется, когда ему удобно). Формат ответа API —
договор, который нельзя нарушать в одностороннем порядке: молчаливое
переименование поля ломает старые клиенты.

## Решение

Все эндпоинты живут под префиксом `/api/v1/` (включая публичные
`/api/v1/integrations/hooks/{id}`; `/health` остаётся без версии — это
инфраструктурный эндпоинт).

Правила внутри версии:

- Добавлять поля в запросы/ответы — можно (старый клиент их не заметит).
- Переименовывать, удалять поля, менять их смысл и коды ошибок — нельзя.
- Ломающие изменения открывают `/api/v1` → `/api/v2`; обе версии живут
  параллельно, пока живы старые клиенты.

Payload событий шины — такой же контракт, как ответ API: поле можно добавить,
переименовывать/удалять нельзя.

## Следствия

- Переход на `/api/v1` выполняется один раз, до первых внешних клиентов
  (сегодня — дёшево, после продаж — дорого).
- Фронтенд, smoke-тесты и мост хаба всегда указывают версию явно.
